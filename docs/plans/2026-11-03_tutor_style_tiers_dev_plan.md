## 3. 实现约定（所有工作包）

上一轮方案第 3 节的 1～10 条继续适用：先读 `AGENTS.md` 和 `node_modules/next/dist/docs/`；沿用现有代码风格；新表只走追加迁移；规则函数是纯函数，要有单元测试；模型调用放在事务之外；不加新依赖（例外是 W0-4 批准的依赖）；不批量改写旧会话；新功能都放在默认关闭的开关后面；界面文字用简体中文。

本轮新增：

11. **提示词只能放在 `prompts/` 下。** 不能在 TS 代码里写新的提示词字符串。改了任何 `.txt` 都要升级 `promptConfigVersion`，并更新 `tests/prompts.test.ts` 里的哈希。
12. **批改和速刷的请求逐字节不变**，除非工作包明确要求改动。每个工作包都要用测试证明这一点（第 4 节 WP1 会建立这项测试）。
13. **调用内容和提示词绝不离开服务器。** 任何接口返回、页面、导出文件、报错信息和日志里，都不能出现 `llm_call_payloads` 表里的数据或提示词原文。
14. **需要真实模型的验证**（行为用例、档位实测）用单独的脚本运行，不放进 `npm test`。脚本的输出和花费写进报告。不能用生产环境的 key 做压力测试。
15. 新的 `llm_calls` 字段一律允许为空。不修改已有的 CHECK 约束。

### 3.1 从不变量推导实现边界

1. **学生内容、使用偏好、一次执行的配置，是三种不同的数据。** 作文与评分继续使用现有会话锁；偏好只决定下一次新操作；执行配置一经接受就冻结。模型晚到的回复不得改写偏好。
2. **给模型看的内容是明确的输入协议，不是整个业务对象。** 在 WP1 建立白名单投影，包含既有输入字段及其原有顺序；新的调用 ID、风格、档位、评分来源和 UI 状态不得自动进入模型上下文。
3. **一致性必须写清比较基线。** 记录、存储和 UI 的改动不能改变模型请求；提示词和档位的改动只允许改变它们负责的部分，见 3.2。
4. **观察失败可以降级，约束失败必须阻止派发。** 观测日志或内容副本写入失败不阻止模型；配置快照或强制额度预留写入失败则不得调用模型。
5. **先维持已知可用的预算，再凭证据调整。** 不把 20 次样本算出的 p99 当成稳定的容量估计；不因为高档位就自动放宽等待时间。

### 3.2 请求一致性的三种基线

| 基线 | 比较对象 | 允许变化 |
|---|---|---|
| B0 原始基线 | 固定 `90f5655` 的请求体字节；14 个逻辑调用点，包含已有重试提示 | WP1 全部不变；此后批改和速刷始终不变 |
| B1 风格基线 | WP4 验收版本、固定会话与同一风格、尚未引入档位的请求 | WP5 后关闭档位时完全不变；包含开关组合 `STYLES_ENABLED=true, TIERS_ENABLED=false` |
| B2 档位对照 | 同一会话快照、同一调用点、同一风格，不同档位 | `messages` 逐字节相同；仅版本化配置允许的推理参数、输出预算等字段可以变化 |

WP3 之后即使三个开关都关闭，对话提示词也仍是通过 A1 验收的新 Standard，不承诺退回 B0；退回旧提示词需要回滚代码。WP3/4 有意变更对话提示词，必须以行为评测验收，不能偷偷更新 B0 使测试通过。

基线在改动前生成并审核，保存会话样例、期望请求体和来源提交号。使用已有 `node:test` 假 fetch、`t.mock.timers` 和 `t.mock.method(crypto, "randomUUID", …)` 固定时间与 ID，捕获实际 `init.body`，不对请求 JSON 排序或删除字段后再比较。会话消息 ID 与新增调用记录 ID 使用独立的固定测试序列，避免新日志消耗 UUID 序列造成假差异。还要覆盖连续两轮对话、评分后总结、重试和新元数据已存在的会话。基线含提示词，只能保存在服务器侧测试目录，不得进入静态资源或公开报告。

### WP1 调用记录与输入边界（LG-01～LG-06）

- **LG-01 调用点表。** 新建 `lib/llm/call-sites.ts`，用 `Record<CallSite, { purpose, group }>` 实现 RFC §3 的表。`llmPurposes` 增加 `writing_check`、`memory_summary`；`diagnosis`、`idea_extract`、`opening` 保留但不再使用。
- **LG-02 精练调用都传 options。** `runAction` 增加参数 `ctx: { userId, operationId }`，`operationId` 取路由的 `requestId`。`app/api/sessions/[id]/actions/route.ts` 和 `lib/pipeline/retry-review.ts` 都要传进来。8 处 `generateJson` 代码覆盖 12 个精练逻辑调用点；全部传 `{ purpose, userId, sessionId, operationId, callSite }`。共用分支必须根据动作区分 chat、clarify、polish、express、check，不能统一标成 chat。
  - 注意 `client.ts:77` 的 `!options` 分支：传了 options 之后，超时会按另一种方式分类。保持学生看到的报错文字不变，并补测试。
  - 除此之外，模型调用的行为不变：请求体、输出上限、超时和重试次数都和现在一样。
- **LG-03 `llm_calls` 新字段。** 加入 RFC §4.2 的全部字段，都允许为空，不改 CHECK 约束。同步修改 `CallRecord`、插入语句（`calls.ts:32-33`）、元数据 zod schema（`calls.ts:25`），以及 `consumeReservation` 的字段比对。这一阶段只写入 `call_site`、`stage_group`、`provider`、`prompt_version`、`finish_reason` 和 `reasoning_tokens`（`readUsage` 要读取 `completion_tokens_details.reasoning_tokens`，如果供应商返回的话）。其余字段等 WP4、WP5a 再写入。
- **LG-04 `llm_call_payloads` 表。** 字段：`call_id`（主键，外键指向 `llm_calls.id`，级联删除）、`user_id`（外键指向 `users`，级联删除）、`session_id`、`created_at`、`expires_at`（创建后 90 天）、`request_json`、`response_text`。索引：`(expires_at)`、`(user_id, session_id)`。
  - 调用结束后写入，成功或失败都写；写入失败不影响这次调用。
  - 写入时顺带删除最多 500 条已过期的记录；`instrumentation.ts` 启动时也清理一次。
  - 不保存 `reasoning_content`。
  - 删除练习时（`lib/db/queries/sessions.ts` 的 `deletePracticeContent`）同时删除这次练习的调用内容。
  - 速刷调用也写入。
- **LG-05 消息关联调用。** `CoachMessage` 增加可选字段 `callId`（`lib/prototype/types.ts`）。精练的教练消息写入这个字段。旧消息没有这个字段，照常显示。
  - 一次 provider 尝试对应一行记录与一个 `callId`；同一操作的重试共用 `operationId`。教练消息关联产生该回复的成功尝试，不能关联失败的第一次尝试。固定开场没有模型调用，不编造 `callId`。
  - 在生成客户端增加可选的成功尝试元数据回调，继续返回原有的 schema 结果；不要把 `callId` 塞进模型输出或 schema。
- **LG-06 输入投影。** 为历史消息及后续会被再次送入模型的评分、对比等对象定义白名单投影。保留 B0 中已有的字段、顺序和缺省语义（包括原有 ID），只阻止新增元数据进入请求。WP5 写入评分来源后仍用同一投影。分隔线属于视图，不创建伪造的 user/coach 消息。
- 调用内容仅保存实际请求体和可获得的输出文本，绝不保存 Authorization、API key、推理过程或异常对象。无响应的失败允许 `response_text=null`。保留日志与内容写入失败的非致命性。
- 防止“删除后晚到的调用重新写回内容”：内容表对 `(user_id, session_id)` 关联会话所有权并级联删除；会话已不存在则跳过内容写入。调用记录仍按既有规则保留。加入删除与模型完成交错的测试。

**验收测试**

- 12 个精练调用点和 2 个速刷调用点分别覆盖；chat、clarify、polish、express、check 还要各覆盖写作与改写两个环节。一次实际尝试一行 `llm_calls`，`call_site`、`purpose`、`stage_group` 都正确。
- 新增 `tests/request-parity.test.ts`，按 3.2 固化 B0。增加多轮用例，确认新增 `callId` 后第二次请求仍不变。
- 超时、供应商报错、不合格输出、输出被截断（`finish_reason=length`）这四种情况，`outcome` 和 `finish_reason` 都记录正确；学生看到的报错文字和改动前一样。
- 调用内容：成功和失败的调用都写入；写入失败（用触发器模拟）时，调用仍然成功；过期记录被清理；删除练习后，这次练习的调用内容为空；删除账户后，这个用户的调用内容为空。

### WP2 练习导出 PDF（EX-01～EX-04）

开始前必须先完成 W0-4（新依赖获得批准）。

- **EX-01 文档模型。** `lib/export/practice-document.ts`：一个纯函数，把 `SessionState` 转成文档模型，即一组段落（标题、正文、分数表、列表），内容按 RFC §9。这个函数不碰任何内部字段：不包含模型、档位、风格、id、`callId`。
- **EX-02 PDF 渲染。** `lib/export/render-pdf.ts`：把文档模型渲染成 PDF，嵌入中文字体的子集。版式简单就行：A4 页面，标题、小标题、正文，加上页码。
- **EX-03 接口。** `GET /api/sessions/[id]/export`：使用 `runtime = "nodejs"`；`requireApiUser`；用 `getSession(user.id, id)` 读取；不是自己的练习或练习不存在都返回 404；速刷练习返回 409 `unsupported_session`。响应头按 RFC §9。放在 `EXPORT_ENABLED` 开关后面，开关关闭时返回 404。
- **EX-04 入口。** 作文页反馈之后的各阶段，以及作文库，都加上"导出 PDF"按钮，并附上微信内置浏览器的提示。

**验收测试**

- 文档模型：对 4 种会话样例分别测试：只有原稿；有改写和对比；模考；包含英文讲解的会话。各段落齐全；结构只包含允许的段落字段；给内部元数据注入独特标记，确认输出不含这些标记或提示词片段。不以全文搜索 `id`、`model` 等普通词判断泄漏，学生正文合法出现这些词应照常导出。
- 接口：未登录返回 401；别人的练习返回 404；速刷练习返回 409；开关关闭时返回 404；成功时响应头正确，内容以 `%PDF` 开头。
- 实现者把生成的 PDF 渲染成图片附在报告里：中文、英文和标点都显示正确，没有方框乱码；长作文能正确分页。
- 浏览器：在桌面和手机宽度下点击按钮，都能下载文件。

### WP3 提示词五层结构（ST-01～ST-04，即 A1）

开始前必须先完成 W0-3（生产数据）。

- **ST-01 新文件。**
  - `prompts/system/coach-preamble.txt`：L0 加 L1，按 RFC §6.1 和 §6.2。
  - `prompts/style/<调用点>/standard.txt`：对 `prewrite`、`chat`、`clarify`、`issue` 四个调用点各写一个，内容就是从现有指令里移出来的详略措辞。
  - 修改 `prompts/coach/{prewrite,chat,clarify,issue}.txt`，去掉其中所有关于详略的措辞。
  - 修改 `prompts/coach/nudge.txt`，让它使用新的 preamble，但不加风格段。
  - `polish`、`express`、`check` 同样使用新 preamble 和 L2/L3，不加 L4；逐个保留句子级改写的 C4 例外。`express` 的“1～2 个句子级建议”是任务范围约束，不得被“删除 short 关键词”的机械测试误删。
  - **不改** `prompts/judge/*`、`prompts/quick/*` 和 `system/preamble.txt`。
- **ST-02 拼装。** `buildMessages` 增加一个参数，用来选择 preamble 和可选的风格段。对话类调用按 RFC §6.1 的顺序拼装；批改和速刷仍然走现在的拼装方式。估算输入长度时，要用包含风格段在内的完整消息。
- **ST-03 长度硬上限。** 每个对话类调用点各自使用一个 schema，`reply` 的最大长度采用 W0-3 校准后的数值（RFC §6.5）。
  - 四个风格调用点按生产数据校准；`polish / express / check` 的 `reply` 暂保留现有 12,000 字符上限，建议数组与改写字段保持现有限制；nudge 使用原有 `message <= 500`。本轮不顺便缩紧无风格调用点的输出。
  - W0-3 对无法从历史 stage/action 唯一确定调用点的样本单列“无法归类”，不推测归类。按调用点和语言分别统计样本量、中位数和 p90；稀疏样本仅作初值，用固定用例补测。
- 升级 `promptConfigVersion`（例如 `coach-json-v5-layers`），并更新提示词哈希测试。
- **ST-04 行为评测脚本。** 新建 `scripts/verify-coach-behavior.ts`，需要真实模型。用例放在 `data/coach-cases/*.json`（新文件）。评测方式：由一个模型按 C1～C5 的评分表打分，并统计回复长度。可以参考 `scripts/verify-quick-behavior.ts`。输出一张表：每个用例在每种配置下的违规次数，以及长度的中位数。WP4 和 WP5 也会用这个脚本。

**验收测试**

- `tests/request-parity.test.ts`：批改调用点和速刷调用点的请求体逐字节不变。
- 拼装：四个风格调用点使用 L0、L1、Schema、L3、L4；另外四个使用 L0、L1、Schema、L3。检查迁出的具体详略句子，不以禁用 `short` 等单词代替语义检查。
- `verify-coach-behavior.ts`：用 RFC §6.7 A2 列出的那几类用例，至少 20 个，在新旧两版提示词下各跑 3 次。C1～C5 违规次数不增加，回复长度中位数的变化不超过 ±20%。报告里附上对比表和花费。

### WP4 风格（ST-05～ST-08，即 A2）

- **ST-05 风格文件。** 为四个调用点各写 `concise.txt` 和 `comprehensive.txt`，按 RFC §6.3 和 §6.4 编写，共 8 个文件，可以放在 `prompts/style/` 下。在 `lib/llm/prompts.ts` 的名称列表里登记，并设立独立的 `styleVersion`。
- **ST-06 设置。** 在 `profile_json` 里加 `tutorStyle`，修改 `DEFAULT_PROFILE` 和 `profilePatchSchema`。账户页加"回复风格"选项（Concise · 简短 / Standard · 标准 / Comprehensive · 详细），放在 `STYLES_ENABLED` 开关后面。
- **ST-07 练习中切换与冻结。** 新增动作 `setTutor`（RFC §10.2），先支持 `style`、`makeDefault` 和 `expectedTutorRevision`，档位部分在 WP5b 补上。按以下规则实现，不重构所有精练动作的锁与 checkpoint。
  1. 为 `writing_sessions` 追加 nullable 列 `tutor_settings_json`，保存 `{ override, revision }`。它是本次练习偏好的唯一来源；旧行为空表示无覆盖。API 可以投影出 `tutorOverride` 和 `tutorRevision`，但 `saveSession` 不把投影字段写回 `state_json`，也不更新该列。旧代码只写 `state_json`，因此不会覆盖新偏好。
  2. `setTutor` 在动作路由内单独分派，校验身份、同源、会话归属与可操作状态；用短数据库事务读取最新偏好，比较 revision，再局部合并并递增 revision。**不占用模型处理期间的会话锁，不写草稿、messages、pendingAction 或会话内容 version。** 冲突返回 409 和最新偏好；`makeDefault` 在同一事务中局部更新账户原始 profile JSON，保留未知字段，账户设置接口使用同样的局部合并边界。
  3. 成功只返回偏好和 revision。前端分别合并偏好与内容；较晚返回的模型请求或轮询不能用较旧的 tutorRevision 覆盖新偏好。选择器立即显示“已设置，下次新请求生效”；当前请求继续显示它实际使用的配置。
  4. 为 `writing_sessions` 追加 nullable、仅服务端读取的 `pending_model_config_json`。新操作在现有会话锁内、第一次派发前，同一短事务写入 pendingAction 与配置快照；重新读取账户和会话偏好，冻结该操作可能使用的所有调用点配置。快照保存 requestId、动作参数哈希、风格/档位、模型、参数、预算和版本、凭据环境变量名，不保存 API key 或提示词正文，不由 `getSession` 返回。
  5. 同一 requestId 的恢复及技术性重试复用快照；不得在每次 `generateJson` 时重新解析偏好。进程重启后从专用列恢复；若所需提示词/配置版本不可用或模型被紧急停用，明确停止恢复，提示发起新请求，不静默改用其他配置。显式“按新设置重试”使用新 requestId；已有完成请求仍沿用幂等返回。成功后清理快照，失败保留至下一次新操作替换；删除会话时随行删除。
  6. 教练消息记录实际使用的 `styleId`（WP5 增加实际档位）。分隔线由相邻已完成回复的配置变化派生，在第一条使用新配置的回复前显示；即时设置确认留在选择器旁。这样正在生成的旧回复不会被画在新配置分隔线下面。历史无标记的回复不推测其实际风格。
- **ST-08 记录。** 在 `llm_calls` 里写入 `style_id` 和 `style_version`。

**验收测试**

- `verify-coach-behavior.ts`：达到 RFC §6.7 A2 的全部标准。跨档位的组合（Comprehensive × Sage）在 WP5c 补测。
- 生效顺序：账户设置为 concise、本次练习切换为 comprehensive 时，下一次调用用 comprehensive；关闭 `STYLES_ENABLED` 时用 standard，`llm_calls` 也记录 standard。
- 冻结：模型调用进行中调用 `setTutor`，这次调用仍然用原来的风格，下一次才用新的风格。
  - 用延迟假 fetch 真正重叠两个请求：切换应在模型结束前成功；旧回复、checkpoint 和前端晚到响应都不能覆盖偏好。另测两个标签页同时切换、`makeDefault` 与账户更新交错、重启后同 requestId 恢复、成功尝试的 `callId` 关联。
- `profilePatchSchema` 拒绝未知的风格值；`profile_json` 里存了未知的值时，读取结果是 standard，原值保留。
- 回滚：用 WP3 代码读写同一数据库，新增列原样保留，旧功能正常；重新升级后偏好仍在。旧模型版本的待恢复操作按版本检查拒绝，不承诺跨代码版本重放。
- 浏览器：在账户页切换风格；练习中切换风格并看到分隔线；手机宽度和深色模式下显示正常。

### WP5c 护栏、实测与校准（TR-04、TR-06、TR-07）

依赖 WP5b。只有本包通过，才允许进入 WP6 的档位启用步骤。

- **TR-04 护栏。** 首版使用下面的明确规则；数值是保守试用建议，放在版本化配置中，后续调整必须有实测依据。
  - 精练每日输出预算默认 **128,000 token / 用户**，按 `Asia/Shanghai` 自然日计；含精练的对话和批改，速刷沿用原来的独立配额。这相当于 8 次现有单尝试输出上限，作为试用资源边界，实际按已用 token 结算。供应商 completion usage 已包含推理时不能再加一次 reasoning tokens。此上限不代表人民币费用或一次练习一定需要这些 token。
  - 派发前原子预留，不能先读 SUM 再无锁调用。原稿评分的必需调用、改写评分与对比的必需调用链，连同允许的技术性重试一起预留上界；可选 review 独立准入，额度不足只标记可选回顾失败，不撤销已提交的评分。费用归属预留所在日，跨午夜不重新计一份。
  - 预留使用独立的精练额度账本，避免把未派发的计划冒充 `llm_calls`。派发后每次尝试的实际 usage 转为已用额度；未派发的余量释放，未知 usage 的已派发调用按该次上限保守计。结算必须幂等；进程中断后回收确定未派发部分，无法确定是否派发的部分保守保留。账本写入失败时拒绝派发；不套用速刷 `Reservation` 的“一次尝试”语义去改变精练重试次数。
  - 配额不足返回 429，说明日限额与重置时间，并写“你的文字已保留”。同 requestId 重放不得重复预留、重复计费；删除练习不释放已消耗额度，删除账户删除其账本。
  - Sage 同时最多 **2 个**活动模型工作流，包含等待和内部重试；保留现有全局 8、每用户 1 的限制。按“现有全局准入 + Sage 子上限”同时检查，失败不占槽位，所有退出路径释放。Sage 自己达到上限不会阻止尚有全局容量的 Adept/Mentor；不承诺全局已满时其他档位仍能调用。
  - 现有准入机制是单 Node 进程范围，本轮部署保持这一前提；多进程扩容前必须把所有并发限制统一移到共享协调层，不能宣称进程内计数能跨进程保护。
  - 护栏在 `TIERS_ENABLED=true` 时强制启用；关档位时返回原有行为，不由新日限额阻断原有练习。即使关档位，新的精练使用记录仍保留，重新打开时统计当日已有使用量。
- **TR-06 实测。** 新建 `scripts/verify-tiers.ts`，仅手动调用、使用非生产测试凭据。先估算最大调用数与费用，默认 dry-run；实际调用有总次数和预算上限。超过单包 ¥50 的执行仍遵守原有负责人确认规则。
  - 先检查官方供应商能力并实际探测每档：HTTP 成功、`finish_reason=stop`、schema 通过只是必要条件。若无法确认低/高/最高参数被支持，停止该档上线，不能根据“返回 200”就宣称三档有区别。
  - 逐个运行合法的“档位 × 8 个对话调用点”组合，nudge 不测 Sage。每组合至少 20 个代表性输入，含长输入、中文与英文；issue 覆盖三级。记录原始样本量、首尝试结果、重试后结果、输出 token、reasoning token（有才记）、延迟 p50/p95、观察最大值和截断/超时比例。20 次不报告可靠 p99，也不据此自动重写对照表。
  - 首轮试用门槛：每组合至少 19/20 在现有超时与重试规则内得到合格结果，观察到的截断为 0；对抗集 C1～C5 经人工复核为 0；Comprehensive × Sage 使用 WP4 同一套用例、每例 5 次。它们是有限样本的验收门槛，不宣称真实故障概率小于 5%。Adept/Sage 不通过可单独停用；Mentor 不通过则不启用档位功能。
  - Mentor 显式 high 与不传参数使用相同固定输入、交错运行，每例至少 5 次，比较行为违规、有效输出率和长度中位数（变化不超过 ±20%）；记录 token/延迟差异。结论只能是“在本测试集内未发现不可接受回归”，不能声称统计等价。
  - 第一轮保持 16,000 / 120 秒规则；只有实际出现截断或不合理浪费时才提出调整。调整后使用未参与选值的固定验证集复验；必要时关闭问题档位，不自动提高预算。最终等待时间来自合格样本的实测分布，并在 WP5b 界面复验。
  - 每次练习成本必须注明假设的调用组成、token 和价格来源日期，实际费用包括评测裁判；不得把模型调用次数直接当成费用。成本总额受上述脚本上限保护，实际生产额度是否适合试用者在小流量观察中再调整。
- **TR-07 校准工具。** 新建 `scripts/judge-calibrate.ts`，读取 `data/judge-calibration/*.json`，记录原配置、候选配置和逐篇逐维度分数。没有校准集时明确退出为“未完成校准”，不能报告通过。门槛为总体及每个评分维度的平均绝对偏移不超过 0.25、单篇各项最大绝对偏移不超过 0.5，避免正负误差抵消。本轮批改配置不变，工具可用合成 fixture 验证；首次更换批改配置前必须使用 W0-5 的真实基准集通过校准。

**验收测试**

- 两个并发请求争夺最后一份额度只允许一个成功；覆盖午夜、技术重试、同 requestId 恢复、进程中断、usage 缺失、写入失败、删除练习后额度不返还。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 传入 options 后超时的分类变了，报错文字也跟着变 | WP1 专门写测试，保证学生看到的报错文字不变 |
| 调用内容表增长太快，备份变大 | 90 天后清理；WP1 报告里估算每次练习的体积 |
| 去掉详略措辞之后，Standard 的回复变长 | A1 单独验收，长度变化不超过 ±20% |
| `deepseek-flash` 不接受 `reasoning_effort` | TR-06 第一项验证；若不支持，不通过 WP5c 的启用门槛，后续模型方案另行决定 |
| Sage 截断或超时太多 | 先保留既有预算；有限样本失败触发独立复验或关闭 Sage，不从 20 次伪造稳定 p99 |
| PDF 库在 Next 里被打包后读不到自己的字体或数据文件 | 加入 `serverExternalPackages`；WP2 报告里说明 |
| 微信里无法下载 PDF | 按钮旁边提示用浏览器打开；报告里记录在微信中的实际表现 |
| 用于评测的真实模型调用花费超出预期 | 每个脚本先估算花费，写进报告；单个工作包超过 ¥50 时先问负责人 |

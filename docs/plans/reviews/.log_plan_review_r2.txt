    42	## 3. Data meanings and ownership
    43	
    44	These are logical records and invariants, not a prescribed SQL layout. Existing session JSON remains the content store; add only the small persistent records needed for these rules.
    45	
    46	| Record | Required meaning |
    47	| --- | --- |
    48	| Attempt | Immutable activity `quick` or `deep`; separate mode `practice` or `mock`; user, question ID/version/exposureKey and prompt snapshot; creation time; latest student-action time; open/set-aside/closed state; schemaVersion separate from the existing optimistic-write version |
    49	| Relationships | `continuedFromQuickId` and frozen card-version snapshot for a Quick continuation; `rewriteOfDeepId` for a Deep rewrite. These are distinct relations, not one overloaded sourceAttemptId. A Deep may have both if it uses a card after prior Deep work |
    50	| Card | Exactly one per (user, Quick attempt); monotonically increasing contentVersion; structured student content/provenance; current check state; last check's contentVersion and check ID |
    51	| Completion | One immutable event per (user, attempt), with activity, question family, frozen primary topic/type, completedAt, originalSubmittedAt (nullable for legacy), freshness (fresh/repeat/unknown), relationship classification and an evidence-present/deleted marker. Session completedAt is only a projection of this event |
    52	| Familiarity | Minimal user × exposureKey facts: first attempt, whether any Deep original was submitted and its first submission time if known, whether prior Deep feedback was made available, external-practice declaration and any unresolved legacy-exposure status |
    53	| Model operation | User/attempt/card version, operation kind, logical operation ID, request/idempotency key, budget package, provider attempts, reservation/usage/time/failure result and configuration version; no essay text in usage logs |
    54	| Checkpoint record | Qualification snapshot at start, timed-submission conditions, declaration, catalog/alias versions, completion result, baseline/trend eligibility and reason codes |
    55	
    56	An attempt's activity never changes. Quick→Deep creates another attempt. Completed work may remain open for optional editing/revision; “completed” is not “closed,” and “set aside” is not “deleted.” Save-for-later keeps the work; an explicit **Set aside** suppresses automatic resume until the student manually resumes it. Opening a page does not change latest student-action time or recommendation order.
    57	
    58	Deleting an attempt deletes its essay/chat content, card and content-bearing check evidence. It retains the minimal familiarity facts, completion/submission markers and non-content budget/operation ledger needed to prevent renewed unseen status, duplicate/misdated statistics and quota resets. Keep originalSubmittedAt and fresh/repeat/unknown on deleted completed-original markers; retain call start times, reserved/known/unknown usage and failure categories even if their source attempt content is deleted. The deletion UI says that text is removed while practice totals and previously-practised status remain. These retained records contain no essay, source excerpt, diagnosis text or score. Counters include these completed-history markers; card counts include only surviving cards. Deleted evidence cannot support recurring focus or be displayed as feedback. Deleting an account deletes all these records, quotas and content.

Checkpoint scheduling may still use its retained completion date.
    61	
    62	## 4. Topic cards, provenance and Quick→Deep
    63	
    64	Card fields follow the actual question: both views plus opinion for discuss_both, paired problems/solutions for problem_solution, both requested answers for two_part, and an appropriate position/reason structure for the other types. Do not require the old universal two-reasons-plus-counterargument template. A check asks whether the student answered the task and supplied relevant reasoning; it does not score a band or mechanically require inapplicable slots.
    65	
    66	Every content part has one honest provenance form:
    67	
    68	1. **Direct edit:** student user ID, server-recorded edit ID/time, card contentVersion, exact entered text. No fabricated message ID.
    69	2. **Selected excerpt:** that user's source message ID, character offsets and exact excerpt. The server verifies ownership, user role and matching original text. Editing the excerpt creates a direct-edit record for the new text; it does not retain a false exact-quote claim.
    70	
    71	Record whether the source was entered after a coach follow-up. This records the context, not proof of independent authorship. Model messages may identify gaps but never write card content. Reuse prewriting conversation/UI only where compatible; do not copy the current model-generated outline slot text into a published card. The existing path in `lib/pipeline/engine.ts` validates a quote but saves the model's own text, so it cannot enforce this invariant unchanged.
    72	
    73	Card states are `draft`, `needs_development`, `passed`, `unchecked`. A check-in-progress or technical failure is operation status, not a student ability judgment. `unchecked` means an edited previously-checked card and is a resumable draft subtype. The review view defaults to passed cards at their currently checked version; the question history exposes every surviving state and a resume/recheck action. Editing a passed card changes it to unchecked without removing its original completion credit. Save/resume/recheck retain the same card ID.
    74	
    75	A check captures immutable card version v before calling the model. Commit its result, card state and first completion event in one short transaction after the call; only apply the result if v is still current and the attempt/account still exists. A stale result may remain operation metadata but cannot pass new content or recreate deleted work. A valid “needs development” result names the gap and keeps the draft. Timeout, invalid JSON and quota exhaustion preserve content and remain technical outcomes. A retry or later pass never adds another Quick completion event.
    76	
    77	**Continue to Deep:** available from a saved Quick card, including a draft. It creates a Deep/practice attempt with the same prompt family and a frozen card-content/provenance/check-state snapshot. No model-written material is added. A default-continuation mapping unique by (user, Quick attempt) returns the same child on repeated clicks, refreshed request IDs or lost responses. This uniqueness applies to the default child, not to every explicitly requested later practice that may cite the same source card. Once that child exists, the default action is Open Deep; a separate explicit New practice action is required for another attempt. If the default child was deleted or explicitly abandoned, say so and require an explicit New practice action rather than silently recreating it. That action creates a separate attempt with its own idempotency key, may copy the current saved card snapshot, and does not overwrite the default-child mapping. Source-card edits do not alter the child. Quick and Deep may finish in different weeks and each earn exactly one credit when its own completion condition is met.
    78	
    79	## 5. One completion definition for every consumer
    80	
    81	- **Quick:** the first valid check that passes the current card version and commits successfully.
    82	- **Deep:** the first successful persistence of the submitted original's required scores and actionable issue feedback, with the feedback available to the student. This is the precise meaning of the earlier phrase “feedback first shown.” Actual viewing is optional separate `feedbackViewedAt` telemetry, not a condition for credit.
    83	- Outline-to-essay review, revision/comparison and closing/plan wording are optional. Failure of one cannot remove or prevent completion once the required original feedback is committed. A partial score without required feedback earns nothing. A failed optional review must be labelled separately from a failed core evaluation.
    84	
    85	All of weekly counts, topic exhaustion, first checkpoint invitation, question-type counts, history labels and pilot metrics consume the same completion events. A completed Deep can still offer revision in history, but is not unfinished for the primary Continue recommendation. Original-submission time is server-recorded when the original snapshot is accepted; completedAt is the successful required-feedback commit time. Both are immutable; optional retries and later edits do not move them.
    86	
    87	Weekly product counts use Monday 00:00 through the next Monday in Asia/Taipei, storing UTC timestamps. A Sunday start completed Monday belongs to Monday's week. Quick followed by Deep earns two activities, but topic breadth counts that question family once. Topic counts show distinct completed questions plus a separate started-only count; card counts show current passed and draft/unchecked cards separately. “Not practised yet” means no attempt record, not merely no completion. Timeouts and drafts are not completed questions.
    88	
    89	Historical `finished` sessions can be marked legacy-completed for all-time counts if that old state is present. Their completion event has `completedAt=null` unless a trustworthy historical completion timestamp exists. Do not infer it from createdAt, updatedAt or migration time. Unknown-time records are excluded from dated weekly totals, recency ranking, pilot comparison, checkpoint scheduling and fresh-original recurrence. They appear in an explicit unknown-date historical count; only known-date Deep completions satisfy recommendation exhaustion and first automatic checkpoint invitation. Merely having legacy evaluation does not prove the required feedback completed. An already legacy-completed event stays unknown-date after regrading; only trustworthy evidence of its original historical completion may fill that missing historical date. Regrading records a separate feedbackUpdatedAt and never a new credit, current-week completion or first-checkpoint trigger. A legacy session with no previous completion event can earn a new current completion only when it genuinely first satisfies the required-feedback contract after migration.
    90	
    91	## 6. Deterministic recommendation and recurring focus
    92	
    93	### Home and recommendation pool
    94	
    95	Home order: (1) the most recently student-edited open, uncompleted, non-set-aside attempt, (2) a due checkpoint invitation, (3) the unranked topic list, (4) last-topic shortcut. Continue can include a reserved question the student deliberately chose. A running operation displays its status and does not create another attempt. A due checkpoint never forces abandonment of current work.
    96	
    97	Inside a topic, define P as the **currently active, non-reserved questions with that primaryTopic**. Reserved questions remain in the full bank with a reserved badge and a note that practising them uses their checkpoint eligibility; they never enter this topic recommendation, including its resume branch. Their direct history/resume links still work.
    98	
    99	**Blocking work** means an open uncompleted Deep original, an open Quick card in draft/needs_development/unchecked state, or an actively started optional Deep revision that has not been closed. Include Set aside work in this exclusion. A passed Quick and a completed Deep with no active revision do **not** block another activity merely because their session is still open. Resume prioritizes required unfinished work and card rechecks; optional revisions remain accessible in history. Every branch that starts new work, including exhausted-topic rotation, uses this same exclusion.
   100	
   101	The question-selection branches below are terminal; activity selection, type ordering and optional focus are separate steps. Stable sorting never depends on page loads or model wording.
   102	
   103	1. **Resume:** among open, uncompleted, non-set-aside attempts on P, select latest student-action time, then latest creation time, then lexicographic attempt ID. Include Deep drafts and Quick draft/needs_development/unchecked cards. A previously completed Quick whose edited card needs recheck is included despite having historical credit. Resume keeps the existing attempt, activity and focus; do not create anything.
   104	2. **No ordinary pool:** if P is empty, return `no_practice_questions`, with the full bank and another-topic actions.
   105	3. **Exhausted:** if every question in P has a known-time Deep completion, first remove questions blocked by existing work as defined below. If none remain, return `only_saved_or_unavailable_work`. Otherwise select the remaining question with the oldest *latest* such completion; tie by bankOrder. Recommend Deep rewrite linked to the latest completed Deep marker on that family. If its text was deleted, show that fact and offer a blank same-question rewrite, never restored content. After completion, that question becomes the most recently completed one. Other topics remain available without auto-ranking them.
   106	4. **Untouched candidates:** P with no familiarity attempt record and no blocking work.
   107	5. **Fallback candidates:** if branch 4 is empty, P without a known-time Deep completion and without blocking work. This includes a completed Quick, a closed/abandoned attempt, or deleted work with retained familiarity. Starting again after abandonment/deletion is explicit and preserves past exposure.
   108	6. **Nothing selectable:** if both candidate lists are empty, return `only_saved_or_unavailable_work`, show saved attempts and manual topic selection. Do not silently override Set aside or manufacture a new attempt. Every legal input has either a recommendation or a specified empty result.
   109	
   110	For a candidate in branches 4–5, prefer the question type with the fewest distinct completed question families across all topics and both pools; count a family once even if Quick, Deep and several rewrites completed. Tie by bankOrder. Recommend Quick only if the topic has neither historical Quick completion nor known-time Deep completion; otherwise recommend Deep. A card is reusable material, not a readiness test. If Deep is selected and a surviving Quick card exists, offer its normal continuation action. An existing active default child is handled by resume/blocking rules. For a deleted or explicitly abandoned default child, recommend the clearly labelled New Deep practice action, requiring confirmation of that action rather than an automatic replacement; it preserves the old default-child mapping. An attempted question without usable card material can still be practised in Deep. Free choice of either activity remains available.
   111	
   112	### Fresh originals and canonical issue codes
   113	
   114	Each user's first accepted Deep-original submission for an exposureKey is the only potentially fresh original on that family. Further submissions on the same family, whether started through a recommendation, free choice, a new ID alias or a rewrite button, are repeat evidence. A known prior feedback marker also makes a later submission repeat evidence. Revision submissions never qualify. Quick coaching alone does not disqualify the first Deep original; record assistance/mode, and distinguish it from a timed checkpoint. An explicit rewrite relation always disqualifies freshness. Allocate this first-submission fact atomically, so parallel free entries cannot both be fresh.
   115	
   116	For focus, select the **two latest completed fresh-original markers**, ordered by originalSubmittedAt and then attempt ID, including markers whose essay evidence was deleted. Only after selecting the two positions check whether their evidence survives. Both must still have usable feedback evidence and the same supported taxonomy version. Do not replace a missing, deleted or unknown-code result with an older convenient essay to manufacture two supporting results: insufficient evidence means no focus. A code qualifies only if it was positively reported in both, fits the chosen question type and is not excluded by the student. T06 is limited to agree_disagree/discuss_both. Tie among qualifying codes by the declared taxonomy order; the explanation cites the actual two essays and dates. Focus never changes the selected question. Missing from a short issue list means “not reported,” not “assessed absent” or “resolved.”
   117	
   118	New diagnosis inputs supply the versioned code definitions; outputs validate against that code set with essay evidence. Current `evaluation.issues[].code` is a free string and the current scoring prompt does not provide the taxonomy: copying that contract into the new rule is insufficient. Unknown or legacy free codes may remain visible as historical feedback but cannot be guessed into T/L codes or qualify for this rule. If the two selected originals lack valid taxonomy evidence, omit focus. A focus-enabled release must validate this contract; no focus is the deliberate fallback.
   119	
   120	## 7. Checkpoints, prior practice and deletion
   121	
   122	The baseline claim is deliberately limited: **a timed, unassisted original on a question not previously practised in this app, with the student reporting no prior outside practice**. It is not proof that the student has never seen the text. Browsing the public bank alone does not disqualify under this definition. UI wording must communicate this limited claim rather than an unqualified “independent unseen question.”
   123	
   124	First automatic invitation: after the first known-time Deep completion, unless an eligible checkpoint already completed. Thereafter, due 14 days after the last eligible checkpoint's completedAt. Skipping sets deferredUntil to now + 7 days; skipping again moves that deferral forward. Failed, abandoned and ineligible repeat mocks do not reset the 14-day clock. Before any eligible completion, the first invitation remains due except during deferral. Creating a checkpoint sets an in-progress action rather than showing another start invitation.
   125	
   126	States: `available` (due and a possible qualified question exists), `deferred`, `in_progress`, `unavailable` (due but none eligible). Unavailable offers a clearly labelled repeat mock that cannot establish or update the eligible baseline/trend. Selection prefers eligible reserved questions, then eligible ordinary questions; within a pool prefer the type with fewest eligible checkpoint completions, then bankOrder. Availability is provisional until the start transaction and declaration check.
   127	
   128	At start, require no prior app attempt on the exposureKey, known legacy exposure and an explicit outside-practice declaration (`no`, `yes`, `unsure`). `yes` marks external practice; `unsure` marks unknown; neither qualifies. Show another candidate or an ineligible mock option. The declaration alone cannot erase app attempts or unresolved legacy history. Check eligibility before creating this attempt's exposure record, so the attempt does not disqualify itself. Persist the decision/evidence and allocate the active checkpoint atomically; the same user cannot start two active checkpoints, or another attempt on that family while a qualifying checkpoint is in progress. Use existing single-process controls and short transactions; no new distributed platform is assumed.
   129	
   130	A qualifying checkpoint is Deep/mock: no coaching or card material before the original is submitted, 40 minutes of server wall-clock time from start, no pause/reset on refresh. The original must be accepted by the deadline; late submissions can still receive feedback but become ineligible. Timer pauses, client-reported elapsed time or later retries cannot turn a late submission into an on-time one. Scoring may finish after the deadline; preserve the original submission time. On completion, verify stored start qualification and timing/assistance facts again. The first completed eligible checkpoint becomes the immutable baseline reference; later eligible results form its trend. Practice scores and ineligible/unknown mocks are displayed separately. Deletion behavior is defined in section 3.
   131	
   132	An attempt-start or prior-practice record survives deleting the essay, so a practised reserve never becomes unseen by cleanup. A newly registered user with no imported history has known app history. For existing users, resolve old built-in IDs and uniquely matching normalized text through a versioned alias map (Unicode NFKC, case-fold, whitespace collapse; no fuzzy guess). Ambiguous or unmatched old content creates uncertainty: conservatively mark **all exposureKeys in the catalog at the migration cutoff** unknown for that user until the unmatched history is resolved. Resolving an alias recomputes the affected uncertainty while preserving positive attempt facts. Truly new question families added after that cutoff can be known if they are not equivalent to an old task; relabelling a key cannot bypass uncertainty. Unknown legacy mock scores stay visible as history, excluded from the baseline.
   133	
   134	## 8. Provisional Quick budget and recovery
   135	
   136	These provisional limits are adopted for design/local testing, not claimed to be validated for a particular model. They apply only to Quick operations. The current shared client's 16,000-output-token, roughly 120-second logical-call budget must not silently apply to Quick.
   137	
   138	| Initial package per Quick attempt | Limit |
   139	| --- | --- |
   140	| Coach follow-ups | At most 2, one focused question each; no need to use both |
   141	| Checks | 1 initial check + 1 student-requested recheck |
   142	| Retry allowance | 1 additional provider attempt shared across all initial operations; automatic retry only for malformed/incomplete output, manual technical retry uses the same allowance |
   143	| Total provider attempts | At most 5: 2 follow-ups + 2 checks + 1 retry |
   144	| Input | At most 4,000 tokens per full request including instruction, schema and supplied content |
   145	| Output | Follow-up at most 512 tokens; check at most 768 |
   146	| Per provider attempt | At most 25 seconds and no longer than remaining package/user time budget |
   147	| Package waiting | At most 100 cumulative seconds of model wait, including failures/retries, excluding student thinking |
   148	
   149	Maximum initial input is 20,000 tokens; maximum output is 2 × 512 + 3 × 768 = 3,328. These are ceilings, not target usage. Five calls cannot each consume 25 seconds because the 100-second package limit wins. The full task and card being checked must fit; overlong input is preserved with an editable limit message, not silently truncated and called fully checked.
   150	
   151	**Later rechecks of the same card:** a lifetime two-check cap would break the editable-card promise. A user can explicitly request a **supplemental check package**, no earlier than 24 hours after the last package was granted to that card. It contains one check plus one shared technical retry, no follow-ups, at most two provider attempts, 8,000 input tokens, 1,536 output tokens and 50 seconds total wait, with the same per-call limits. Require changed card content since the last substantive check, or a last check that ended in technical failure. The initial package closes when a supplemental one is granted; unused allowance is not stacked. The card/attempt identity and lifetime usage ledger remain unchanged. Initial follow-ups never reset. This 24-hour recovery rule is a provisional implementation default introduced to close the lifecycle, and may be tuned with evidence.
   152	
   153	**User-wide ceiling, also provisional:** across all Quick attempts and packages in a rolling 24-hour window: at most 15 provider attempts, 60,000 input tokens, 12,000 output tokens and 300 seconds of model wait. All four ceilings apply; creating/deleting attempts, changing request IDs or switching cards does not reset them. Package allowances are bounded by the user's remaining allowance. Show the next eligible recheck time and why a request is blocked. Manual editing, saving, free question browsing and Deep entry remain available; no background top-ups or paid calls occur because a page is opened.
   154	
   155	Reserve call count and worst-case token/time capacity persistently before dispatch. Reconcile with known actual usage/time; keep conservative reservations for indeterminate calls and record provider usage as unknown rather than zero. Persist call start time for rolling-window accounting. Recover a crash's in-flight operation as indeterminate without silently sending it again; an explicit technical retry consumes the existing retry allowance. A provider may still bill an interrupted request, so local cancellation is not proof of zero provider usage. Log operation/config versions, duration, actual-or-unknown tokens and error category, never essay text in usage logs.
   156	
   157	Idempotency is keyed to the logical operation and card contentVersion, not merely the caller's arbitrary request ID. Refresh/repeated clicks return an existing result or running status without new allowance. Rechecking unchanged content with an existing substantive result returns it free; a changed version uses the next permitted check. Retry reruns the failed logical operation on the same snapshot. Content failure (`needs_development`), invalid output, timeout, quota exhaustion and stale result are distinct outcomes. Exhaustion preserves the draft and provides Set aside, manual edit, Deep continuation or the next explicit supplemental opportunity; it never marks the card passed.
   158	
   159	## 9. Migration and release boundary
   160	
   161	The app has no plan_tasks table; `/plan` redirects to `/progress`. Retiring those is not the data migration. The actual baseline is `writing_sessions.state_json`, plus the current unversioned free-code evaluations and process-local session locks.
   162	
   163	1. Add `schemaVersion` independent of optimistic `version`. One adapter reads old and new sessions, maps missing schemaVersion to v1, maps old activities to Deep and retains unknown fields. Persist the upgraded shape only on the next real save; do not batch-rewrite content or invent timestamps. Compatibility views expose unknown completion/evidence explicitly.
   164	2. Establish the canonical catalog/alias map and familiarity cutoff before enabling new recommendation/checkpoint writes. Backfill minimal positive facts from mapped old attempts without altering their content; unresolved history follows section 7. Adaptation alone does not supply reliable history dates or taxonomy evidence.
   165	3. Persist card/provenance, immutable completion facts, exposure and budget operations for correctness. These are not a speculative performance cache. Topic views may join these facts and scan existing session lists for the pilot; a separate optimized attempt-summary cache remains deferred until measured history size justifies it.
   166	4. Keep model calls outside database transactions. Preserve the existing per-session lock across actions, edits and deletes, and transactionally guard the exact new invariants (card version, one continuation, one completion, first original and checkpoint start). The documented single persistent Node process remains the deployment constraint; do not add a second instance without a separate concurrency design.
   167	5. First ship a reader compatible with both schemas, then enable new writes. A rollback target after Quick writes must fully support cards/budgets, or expose Quick read-only and reject its actions clearly. It must retain new tables and unknown fields, never show essay controls on Quick, and never restore a pre-release database over later user work. A read-only rollback may disable new features while preserving their recorded state.
   168	6. Remove model-generated next-session plan wording (`lib/pipeline/engine.ts` finish path). The deterministic rule becomes the only recommendation source. Optional finish wording cannot gate completion.
   169	7. This RFC supersedes mandatory onboarding in 原型/01, task pickup in 原型/02, planning in 原型/11, and conflicting completion/material/bank clauses in 原型/03, 10 and 90 for this feature. Mark those sections during implementation; do not treat their unrealized normalized tables as current storage. The historical docs and concepts brief are retained, not silently synchronized.
   170	
   171	Required rollout checks include saved draft/passed/edited cards, failed and in-flight checks, deletion during requests, lost responses, old unknown-time records, alias ambiguity, read-only rollback, and round-trip preservation of unknown fields. These are requirements, not claims that runtime tests have passed in this documentation task.

   173	## 10. Pilot measurement and acceptance
   174	
   175	The provisional catalog capacity assumes a six-week pilot; three ordinary activities per week is a sizing assumption, not a compulsory assignment. First establish feasibility and usable telemetry. This RFC does not assert a learning-effect gain from a small descriptive pilot.
   176	
   177	Before enrolling the cohort, freeze its dates, enrollment cutoff, catalog/budget/taxonomy versions and metric definitions. User-week denominators include every enrolled user's scheduled observation weeks, including zero-activity weeks and dropouts. Report account-deletion exclusions explicitly and remove their identifiable records rather than pretending they were active users. Use the same completion definition for any comparison; unknown-date legacy work is not a numerical baseline.
   178	
   179	| Outcome | Reproducible definition |
   180	| --- | --- |
   181	| Breadth | Per user-week distinct completed question families, primary topics and types, separately; started-only work is a different metric |
   182	| Deep guardrail | Deep completion events / enrolled observation user-weeks, including zeros; split first originals, repeats and Quick continuations (continuation is also first/repeat, not an extra completion) |
   183	| Card use | Explicit review-open events and usefulness answers with respondent/eligible-user denominators; do not infer usefulness from card count |
   184	| Authorship | Sample whole conversations plus cards, including passed, failed and technically interrupted cases; report coach-supplied arguments separately from honest text provenance |
   185	| Reliability/cost | Operation and provider attempt counts, failure categories, wait distribution and known/unknown tokens; include failed, retried and abandoned work in usage numerators |
   186	| Checkpoints | Invitations, starts, skips, qualified completions and reasons for ineligibility; baseline/eligible trend separate from other mock results |
   187	
   188	For existing users with comparable known-time completion history, report before/after Deep rates using the same denominator and event definition. For new users or incompatible history, report description only; do not claim “Deep did not fall” without a valid comparator. Numerical learning-effect success thresholds and a causal experiment remain later decisions, distinct from the technical pilot entry criteria below.
   189	
   190	| Case | Required result |
   191	| --- | --- |
   192	| Ordinary A/B completed; reserved R untouched | Rotate a Deep rewrite on A/B; never recommend R in the topic rule |
   193	| All ordinary questions have unfinished Deep, no cards | Resume an existing Deep using stable order |
   194	| Four passed Quick cards remain open, no Deep yet | Recommend Deep continuation; completed/open alone is not blocking work |
   195	| Exhausted A/B; A has a set-aside unfinished rewrite | Rotate to B; if both blocked, named empty state; manual resume retains A’s attempt |
   196	| Only set-aside work, or no ordinary questions | Named empty state and manual options; no duplicate/new work by surprise |
   197	| Passed card edited | Same card becomes unchecked; historical credit/time unchanged; recheck checks the new version |
   198	| Directly typed card; selected user excerpt | Honest distinct provenance; coach/other-user sources rejected |
   199	| Quick Sunday, continued Deep Monday; repeated continuation request | Two attempts, two completion events in correct weeks, one normal continuation child |
   200	| Required feedback saved; optional review fails or response is lost | One Deep completion; retry/refresh/finish does not duplicate or move it |
   201	| Free-entry repeat of a question family or alias | Not a fresh original; still a valid completed activity |
   202	| Invalid/free historical issue codes; missing recent evidence | No fabricated focus or resolved claim |
   203	| Valid T06 in latest two fresh originals, incompatible chosen type | No T06 focus; never change question to force the focus |
   204	| Practise reserve, delete essay, attempt checkpoint | Prior practice survives; no new unseen qualification |
   205	| Unknown legacy mapping or external declaration unsure | No eligible baseline from uncertainty; explicit alternate/repeat route |
   206	| Refresh/two tabs/late submission during checkpoint | One active checkpoint, no timer reset, correct late qualification |
   207	| Budget exhaustion, crash, repeated UUIDs, delayed output | No budget reset or duplicate credit; text saved; technical state explicit |
   208	| Later edited card after initial checks used | Explicit same-card supplemental package after cooldown and within user limit |
   209	| Old finished record saved or regraded after upgrade | No invented completedAt or new weekly credit; historical unknown-time count remains separate |
   210	| Delete a Quick with consumed quota or the latest fresh original | Budget remains charged; deleted-original marker retains its position and prevents substituting older focus evidence |
   211	| Compatible rollback with Quick records | Supported lifecycle or read-only rejection; no table/content loss |
   212	
   213	The mock catalog must pass its separate deterministic validation for IDs, quotas, allowed tags/types, provenance locators and duplicate families. Document review and fixture validation do not substitute for the above application tests. Follow-up review findings and their disposition are recorded in [the revision review](../reviews/question_bank_first_practice_revision_review_20261101.md).

    36	| `is_current` | 每个 `id` 只有一个当前版本（部分唯一索引 `(id) WHERE is_current = 1`） |

    38	导入时，同一 `(id, version)` 已存在但内容不同（题干、标签、池、家族任一不同）时报错退出，不覆盖已冻结的版本。

    41

    45	type QuestionRequirements = {

    94	## 4. 完成事件写入点（RFC §5）
    95	
    96	| 活动 | 写入位置 | 条件 |
    97	|---|---|---|
    98	| 精练 | `lib/pipeline/engine.ts` 原稿评估的**第一次模型调用**成功并通过校验之后（`engine.ts:51` 起）。这一次已经返回分数、问题、原因与提示，满足 RFC §5 的“分数与可操作的问题反馈” | 原稿；第一次；同一事务写会话（`evaluation`、`stage = feedback`）与 `completion_events` |
    99	| 速刷 | 13 第 6 节检查结果提交事务 | 第一次通过当前版本 |
   100	
   101	- **第二次调用（提纲回顾）是可选步骤**（RFC §5）：改为独立的 `reviewStatus`（`none` / `pending` / `ok` / `failed`）与单独的重试动作，失败只影响回顾区，不回退阶段、不重跑评分、不影响完成。这是编排与保存边界的调整，评分与诊断的输入不变（G-01）。
   102	- **原稿接受时**（`engine.ts:46` 附近，`state.submitted.original` 写入时）在同一短事务里：写不可变的 `originalSubmittedAt`；按题目家族竞争新原稿资格：`familiarity.deep_original_submitted = none` 且不是关联重写时，这次是 `fresh`，并把它改为 `known`；否则是 `repeat`；家族曝光未知（RFC §7）时是 `unknown`。资格在评分前就定下，评分失败不改变它。
   103	- 粘贴题目也先经 `resolveQuestion`；能解析到家族时按该家族判定，避免绕过重复判定。
   104	- 旧记录（RFC §5 末段）：`stage = finished` 的旧会话在迁移扫描时补一条 `legacy = 1, completed_at = null` 的事件；**不从 `createdAt`、`updatedAt` 推算时间**。有原稿提交或评估的旧会话，把对应家族的 `deep_original_submitted`、`prior_feedback` 记为 `unknown_time`。重评只写会话的 `feedbackUpdatedAt`，不新建事件。

   106	## 5. 推荐（RFC §6）
   107	
   108	### 5.1 函数
   109	
   110	纯函数，放在 `lib/rules/recommend.ts`；输入一次性组装好，不读数据库、不读当前时间。
   111	
   112	```ts
   113	type RecommendInput = {
   114	  topic: string;
   115	  questions: QuestionRow[];          // 当前版本、is_current
   116	  attempts: AttemptView[];           // 该用户全部未删除会话的摘要（activity、questionId、exposureKey、lifecycle、lastStudentActionAt、createdAt、card 状态、是否有进行中的改写）
   117	  completions: CompletionEvent[];    // 含 evidence_deleted
   118	  familiarity: FamiliarityRow[];
   119	  continuations: DefaultContinuation[];
   120	  focusEnabled: boolean;
   121	  focusEvidence: FocusEvidence | null; // 见 5.3；focusEnabled=false 时为 null
   122	  excludedCodes: string[];           // 由 profile.excludedMemoryIds 中 "issue:XXX" 去掉前缀得到
   123	};
   124	
   125	type Recommendation =
   126	  | { kind: "resume"; attemptId: string }
   127	  | { kind: "new"; questionId: string; activity: "quick" | "deep"; continueFromQuickId: string | null; needsExplicitNew: boolean; focus: FocusChoice | null; reason: ReasonParts }
   128	  | { kind: "rewrite"; questionId: string; rewriteOfDeepId: string; sourceDeleted: boolean; reason: ReasonParts }
   129	  | { kind: "empty"; reason: "no_practice_questions" | "only_saved_or_unavailable_work" };
   130	```
   131	
   132	分支顺序、阻挡条件、打平规则、活动选择全部照 RFC §6 实现，代码注释写明对应 RFC 的哪一条。`resume` 只导航到已有练习，不调用创建接口。
   133	
   134	### 5.2 理由文字
   135	
   136	`ReasonParts` 是结构化的（分支、题型是否练得最少、写作重点的两篇证据及日期），由前端 `components/topics/reason.tsx` 拼成中文。日期一律来自证据；不出现“最近”“经常”。
   137	
   138	### 5.3 写作重点
   139	
   140	- 本版本**默认关闭**：环境变量 `FOCUS_ENABLED`，默认 `false`。关闭时 `focus` 恒为 `null`（RFC §1、§6）。
   141	- 打开前提（单独工作包，不在本次 N0～N3 内）：诊断输入带版本化分类表、输出按分类表校验；然后再按 RFC §6 选两篇新原稿。
   142	- `FocusChoice = { code; taxonomyVersion; evidence: [{attemptId, submittedAt}, {attemptId, submittedAt}] }`。写入会话时转换为现有 `Focus`（`{code, name, instruction, reason}`，`lib/prototype/types.ts:24`），`name`、`instruction` 取自 `lib/taxonomy.ts`，`reason` 由 5.2 生成。
   143	
   144	## 6. 检查点（RFC §7）
   145	
   146	- 默认关闭：环境变量 `CHECKPOINTS_ENABLED`，默认 `false`；第 9 节检查点用例全部通过后才打开（RFC §1）。
   147	- 所有创建练习的入口（主题推荐、自由选择、粘贴题目、写成作文）都先检查同一家族是否有进行中的检查点，有则拒绝（RFC §7）。
   148	- 外部练习自报为 `yes` / `unsure` 时，即使这次没有开始检查点，也把自报写入 `familiarity.external_practice`。关闭或删除进行中的检查点时释放占位。
   149	- 纯函数 `lib/rules/checkpoint.ts`：`checkpointState(input, now) → { state: "not_due" | "available" | "deferred" | "in_progress" | "unavailable"; candidateQuestionId?: string }`。
   150	- 跳过：`profile.checkpointDeferredUntil = now + 7 天`。
   151	- 开始：`POST /api/checkpoints/start { questionId, declaration: "no" | "yes" | "unsure", idempotencyKey }`。在一个事务里：重算资格（不先写本次曝光）、插入 `checkpoints(in_progress)`（部分唯一索引保证每人一条）、创建 `activity=deep, mode=mock` 会话、写 `attempt_markers` 与 `familiarity`。不合格返回 `409 checkpoint_ineligible` 并附原因。
   152	- 计时：`deadline_at = started_at + 40 分钟`，服务端时间。原稿提交时比较服务端接收时间与 `deadline_at`；超时仍可评分，但 `status = ineligible`。客户端的 `elapsed` 只用于显示。
   153	- 完成：原稿完成事件写入的同一事务里复核资格，写 `status`、`completed_at`；用户第一条 `eligible` 记录 `is_baseline = 1`，之后不改。
   154	- 进展页（`app/(main)/progress/page.tsx`）：基线与趋势只用 `eligible`；其他模考单独列出并说明原因。

   157	
   158	- `scripts/migrate-0.4.ts`（启动时也会对未扫描的用户执行一次）：对每位用户读出全部会话，经 `readSession` 适配；用别名表解析旧题目；写 `attempt_markers`、`familiarity`、旧完成事件；无法解析的旧练习计入 `legacy_scan.unresolved_count`。**不改写任何会话 JSON**。

   160	- 新注册用户直接写一条 `unresolved_count = 0` 的 `legacy_scan`。

    18	## 2. 卡片内容结构
    19	
    20	```ts
    21	type Provenance =
    22	  | { kind: "direct"; userId: string; editId: string; editedAt: string; contentVersion: number }
    23	  | { kind: "excerpt"; userId: string; messageId: string; start: number; end: number };
    24	
    25	type Part = {
    26	  key: string;                 // 例如 "q1.answer"、"viewA.why"
    27	  text: string;                // 1～600 字
    28	  provenance: Provenance;
    29	  afterFollowUp: 0 | 1 | 2;    // 写入时已经发生过几次追问（只记上下文，不代表独立作者身份，RFC §4）
    30	};
    31	
    32	type CardContent = { layout: QuestionRequirements["layout"]; parts: Part[] };

    36	- `excerpt` 的文字由服务端从**该用户自己**的、`role = user` 的消息原文中按 `start`、`end` 截取；客户端只传位置。编辑一段摘取的文字后，这段的来源改为 `direct`（RFC §4）。

    53	## 4. 动作接口
    54	
    55	走现有 `POST /api/sessions/{id}/actions`，但**不沿用**它“持锁等完整个模型调用、事后统一 `persist(session)`”的做法（`app/api/sessions/[id]/actions/route.ts:19-29`；`lib/pipeline/lock.ts` 遇到并发直接拒绝）。速刷动作按以下方式处理：
    56	
    57	- **不调模型的动作**（`cardSave`、`cardExcerpt`、`quickAnswer`、`continueDeep`）：在一个同步短事务 `commitQuickMutation` 里重读会话与卡片、校验所有者与版本、修改卡片与会话 JSON、`version + 1`、写 `request_receipts`。事务之后不再由路由调用 `persist`。
    58	- **调模型的动作**（`quickFollowup`、`quickCheck`、`quickRetry`）分三段：① 加锁，短事务里写 `quick_operations(running)`、`quick_operation_inputs` 与额度预留，解锁；② 不持锁调用模型；③ 再加锁，短事务里重读最新状态并提交（13 第 6 节第 5 步）。这样检查进行中，学生仍能保存新版本，检查结果会按 `stale` 处理。
    59	- 运行状态读 `quick_operations`，不能用“锁是否存在”来判断。
    60	- `completedRequests` 继续写入，供现有客户端兼容；真正的去重依据是 `request_receipts` 与 `quick_operations` 的唯一键。
    61	- 会话已被删除时，提交阶段不得用现有的 upsert 保存函数把会话重新建出来。
    62	- 新增 `GET /api/sessions/{id}/quick` 返回 `{ session, card, operations, budget }`，用于刷新恢复。
    63	
    64	会话 `activity` 不是 `quick` 时这些动作返回 `409 unsupported_session`。所有动作的响应统一为 `{ session, card, operations, budget }`，其中 `budget` 是剩余额度和下次可申请复检的时间。速刷页面使用自己的客户端状态控制器，不复用现有 `SessionProvider` 的“忙碌”判断。
    65	
    66	| 动作 | 请求 | 处理 |
    67	|---|---|---|
    68	| `cardSave` | `{ cardVersion, parts: Array<{key, text}> }` | 版本不等于当前 `content_version` 时返回 `409 card_conflict`；改动的 part 写 `direct` 来源；`content_version + 1`；`passed` 改为 `unchecked` |
    69	| `cardExcerpt` | `{ cardVersion, key, messageId, start, end }` | 校验消息属于本会话、本用户、`role = user`、位置合法；写入原文 |
    70	| `quickAnswer` | `{ text }` | 学生回答追问，存为对话消息，不进卡片 |
    71	| `quickFollowup` | `{ cardVersion }` | 见第 5 节 |
    72	| `quickCheck` | `{ cardVersion }` | 见第 6 节 |
    73	| `quickRetry` | `{ operationId }` | 用同一快照重跑失败的操作，消耗共享重试额度 |
    74	| `quickSupplemental` | `{}` | 申请补充检查包（RFC §8），条件不满足时返回原因与可申请时间 |
    75	| `continueDeep` | `{ explicitNew: boolean, idempotencyKey }` | 见第 7 节 |

    77	## 5. 追问 `quick_followup`
    78	
    79	- 额度：先在一个短事务里**持久化预留**本次调用（次数、输入上限、输出 512、时长 25 秒，且不超过包内与用户 24 小时剩余额度，RFC §8），再在事务外调用模型，返回后再用短事务核销实际用量。**预留写入失败就不调用模型**；核销失败时保留预留。每一次自动重试都重新预留，并消耗包内共享的那一次重试额度。
    80	- 输入：题目、本题 `subquestions`、当前卡片、本次已有的追问与学生回答；整个请求不超过 4,000 tokens，超出时返回提示、不截断。
    81	- 输出 Schema：`{ question: string /* ≤80 字，以问号结尾 */, targetKey: string | null }`。
    82	- 规则（提示词 + 行为用例 16、17）：只问一个问题；不给论点、例子或结论；可以给思考方向；不评价立场。
    83	
    84	## 6. 检查 `quick_check`
    85	
    86	1. 取卡片版本 v 的不可变快照。同一版本已有实质结果（通过或还需展开）时直接返回该结果，不消耗额度（RFC §8）。
    87	2. 代码从本题 `subquestions` 和 `layout` 生成要求清单：`{ id, zh, keys[] }`。槽位为空的要求直接判为缺，不送模型；全部为空时不调用模型，也不消耗检查次数。
    88	3. 预留额度（输出 768）→ 事务外调用模型 → 输出 Schema：
    89	
    90	   ```ts
    91	   { results: Array<{ id: string; status: "met" | "gap"; note: string | null /* gap 时 ≤60 字 */ }> }
    92	   ```
    93	
    94	4. 校验：覆盖每条送出的要求且没有多余的；`note` 不超过 60 字，且不含 6 个以上连续英文单词（防止写出示范句）。不合格时，若共享重试额度还在就自动重试一次，否则记 `invalid_output`。
    95	5. 提交：在一个短事务里，**只有当前 `content_version` 仍等于 v、练习和账户都还在时**才写入卡片状态、`quick_check_results`、`last_check_id`，以及第一次通过时的 `completion_events`。否则这次操作记为 `stale`，不改卡片（RFC §4）。
    96	6. 规则：只看是否回答了题目的每个要求、有没有相关的理由；不看观点好坏，不打分。
    97	
    98	## 7. 写成作文（RFC §4）
    99	
   100	- `continueDeep { explicitNew: false }`：查 `default_continuations`。已有子练习就返回它（“打开作文”）；已删除或已放弃时返回 `409 default_child_gone`，界面提示需要明确选择“另开一次练习”；没有就在事务里创建 `activity=deep, mode=practice` 的新会话，写入 `continuedFromQuickId` 和卡片快照（`cardSnapshot`：内容、来源、检查状态、版本），并写映射。
   101	- `continueDeep { explicitNew: true }`：按 `idempotencyKey` 去重，创建另一次练习，复制当前卡片快照，不改映射。
   102	- 精练会话的写前与写作阶段，左栏显示 `cardSnapshot`（只读）。之后改动原卡片不影响这份快照。
   103	
   104	## 8. 恢复
   105	
   106	- 服务启动时，把 `quick_operations.status = running` 的记录改为 `indeterminate`，预留额度保持扣除，不自动重发（RFC §8）。界面显示“上次检查没有完成”，提供使用重试额度的按钮；重试读取 `quick_operation_inputs` 中冻结的输入，不用当前卡片代替。
   107	- 刷新或重复点击：同一 `(kind, card_version)` 已在运行时返回运行状态，不新建操作。
   108

    51	## 认证与数据边界
    52	
    53	密码使用随机盐和 scrypt 哈希。浏览器仅保存随机会话令牌，数据库保存令牌的 SHA-256 哈希；会话有效期 30 天。Cookie 使用 `HttpOnly`、`SameSite=Lax`，生产环境额外开启 `Secure`，因此生产访问必须通过 HTTPS。
    54	
    55	修改密码会撤销原有会话并给当前浏览器签发新会话。异步密码验证之后会再次核对数据库中的密码版本，避免并发修改时使用过期凭据登录或覆盖新密码。退出会撤销当前会话。账户删除要求当前密码和确认文字，并通过外键级联删除认证会话及写作记录。
    56	
    57	所有业务 API 从认证 Cookie 获取用户 ID，不接受调用方指定数据所有者。写作记录的主键包含用户 ID，查询、更新与删除均带所有者条件。不存在和属于其他人的练习都返回 404。账户删除期间尚未完成的模型返回不能重新创建已删除数据。
    58	
    59	写操作检查完整 Origin，并校验 JSON 输入与请求体大小。登录限流使用数据库中的账户标识和全局计数，不信任客户端发送的 IP 头；伪造 `X-Forwarded-For` 不会重置次数。全局限流是基础保护，公开部署仍应根据实际流量配置入口层请求限制。
    60	
    61	用户资料保存在 `users.profile_json`，练习完整状态保存在 `writing_sessions.state_json`。学习记忆和进展从当前用户的反馈记录派生，记忆排除项保存在用户资料中。使用教练、评估或改写功能时，必要的作文、题目、对话和学习偏好会发送给配置的模型服务。数据库与备份包含个人学习数据，需要由部署者限制文件访问。

   114	## 数据库迁移
   115	
   116	SQLite 启用 WAL、外键检查与 5 秒锁等待。事务保持短小，模型调用在事务外执行。
   117	
   118	首次连接会幂等建立当前基线表，让全新本地环境可以直接运行。首个 SQL 迁移使用 `IF NOT EXISTS`，因此在基线初始化之后执行 `db:migrate` 不会重复创建表或索引。迁移日志仍由 Drizzle 管理；后续结构变更需要正式迁移，不能依赖基线初始化升级现有表。
   119	
   120	修改结构时：
   121	
   122	1. 更新 `lib/db/schema.ts`，执行 `npm run db:generate`。
   123	2. 审查 SQL，对新库和已有数据分别验证迁移。
   124	3. 同时提交 Schema、SQL 与 `drizzle/` 元数据。
   125	4. 升级环境先备份，在维护窗口由单个进程执行迁移，再启动新应用。
   126	
   127	已经应用的迁移不要重写；追加迁移表达后续变更。不在有数据的环境用 `drizzle-kit push` 代替迁移历史。基线初始化只负责第一版 Schema；未来增加表或列时，不应把升级逻辑重复写进该初始化函数。
   128	
   129	## 部署与备份
   130	
   131	当前支持单个常驻 Node 进程和持久本地磁盘。会话操作锁位于进程内，不能直接部署为多个 Node 副本或临时文件系统上的无状态函数；扩容前需要共享事务锁或队列及相应数据库迁移。
   132	
   133	对外部署需要 HTTPS。反向代理应保留外部 Host，`APP_ORIGIN` 填实际访问源；代理和平台的请求超时需要覆盖模型请求时间，长评估路由允许最长 300 秒。设置绝对 `DATABASE_PATH` 指向持久磁盘，重部署必须保留该目录。使用 Node.js 24 安装和构建，在停机升级期间执行：
   134	
   135	```sh
   136	NODE_ENV=production npm run db:migrate
   137	npm run build
   138	npm start
   139	```
   140	
   141	`npm run db:backup` 读取现有数据库并生成带 UTC 时间与随机 ID 的备份；源文件不存在会报错。该命令不自动安排定时备份或异机存储，应在部署环境中单独配置。
   142	
   143	恢复时停止应用，将完成的备份复制到新目录，避免混入旧的 `-wal` / `-shm` 文件。把 `DATABASE_PATH` 指向恢复文件，检查 SQLite 完整性，执行对应版本迁移，再启动应用并验证账户与练习。
   144	
   145	不要直接复制运行中的单个 `.db` 文件作为备份，也不要让多台机器通过网络共享目录同时访问它。定期在独立目录演练恢复。

   144	## 6. 检查点（RFC §7）
   145	
   146	- 默认关闭：环境变量 `CHECKPOINTS_ENABLED`，默认 `false`；第 9 节检查点用例全部通过后才打开（RFC §1）。
   147	- 所有创建练习的入口（主题推荐、自由选择、粘贴题目、写成作文）都先检查同一家族是否有进行中的检查点，有则拒绝（RFC §7）。
   148	- 外部练习自报为 `yes` / `unsure` 时，即使这次没有开始检查点，也把自报写入 `familiarity.external_practice`。关闭或删除进行中的检查点时释放占位。
   149	- 纯函数 `lib/rules/checkpoint.ts`：`checkpointState(input, now) → { state: "not_due" | "available" | "deferred" | "in_progress" | "unavailable"; candidateQuestionId?: string }`。
   150	- 跳过：`profile.checkpointDeferredUntil = now + 7 天`。
   151	- 开始：`POST /api/checkpoints/start { questionId, declaration: "no" | "yes" | "unsure", idempotencyKey }`。在一个事务里：重算资格（不先写本次曝光）、插入 `checkpoints(in_progress)`（部分唯一索引保证每人一条）、创建 `activity=deep, mode=mock` 会话、写 `attempt_markers` 与 `familiarity`。不合格返回 `409 checkpoint_ineligible` 并附原因。
   152	- 计时：`deadline_at = started_at + 40 分钟`，服务端时间。原稿提交时比较服务端接收时间与 `deadline_at`；超时仍可评分，但 `status = ineligible`。客户端的 `elapsed` 只用于显示。
   153	- 完成：原稿完成事件写入的同一事务里复核资格，写 `status`、`completed_at`；用户第一条 `eligible` 记录 `is_baseline = 1`，之后不改。

    53	## 4. 动作接口
    54	
    55	走现有 `POST /api/sessions/{id}/actions`，但**不沿用**它“持锁等完整个模型调用、事后统一 `persist(session)`”的做法（`app/api/sessions/[id]/actions/route.ts:19-29`；`lib/pipeline/lock.ts` 遇到并发直接拒绝）。速刷动作按以下方式处理：
    56	
    57	- **不调模型的动作**（`cardSave`、`cardExcerpt`、`quickAnswer`、`continueDeep`）：在一个同步短事务 `commitQuickMutation` 里重读会话与卡片、校验所有者与版本、修改卡片与会话 JSON、`version + 1`、写 `request_receipts`。事务之后不再由路由调用 `persist`。
    58	- **调模型的动作**（`quickFollowup`、`quickCheck`、`quickRetry`）分三段：① 加锁，短事务里写 `quick_operations(running)`、`quick_operation_inputs` 与额度预留，解锁；② 不持锁调用模型；③ 再加锁，短事务里重读最新状态并提交（13 第 6 节第 5 步）。这样检查进行中，学生仍能保存新版本，检查结果会按 `stale` 处理。
    59	- 运行状态读 `quick_operations`，不能用“锁是否存在”来判断。
    60	- `completedRequests` 继续写入，供现有客户端兼容；真正的去重依据是 `request_receipts` 与 `quick_operations` 的唯一键。
    61	- 会话已被删除时，提交阶段不得用现有的 upsert 保存函数把会话重新建出来。
    62	- 新增 `GET /api/sessions/{id}/quick` 返回 `{ session, card, operations, budget }`，用于刷新恢复。
    63	
    64	会话 `activity` 不是 `quick` 时这些动作返回 `409 unsupported_session`。所有动作的响应统一为 `{ session, card, operations, budget }`，其中 `budget` 是剩余额度和下次可申请复检的时间。速刷页面使用自己的客户端状态控制器，不复用现有 `SessionProvider` 的“忙碌”判断。
    65	
    66	| 动作 | 请求 | 处理 |
    67	|---|---|---|
    68	| `cardSave` | `{ cardVersion, parts: Array<{key, text}> }` | 版本不等于当前 `content_version` 时返回 `409 card_conflict`；改动的 part 写 `direct` 来源；`content_version + 1`；`passed` 改为 `unchecked` |
    69	| `cardExcerpt` | `{ cardVersion, key, messageId, start, end }` | 校验消息属于本会话、本用户、`role = user`、位置合法；写入原文 |
    70	| `quickAnswer` | `{ text }` | 学生回答追问，存为对话消息，不进卡片 |
    71	| `quickFollowup` | `{ cardVersion }` | 见第 5 节 |
    72	| `quickCheck` | `{ cardVersion }` | 见第 6 节 |
    73	| `quickRetry` | `{ operationId }` | 用同一快照重跑失败的操作，消耗共享重试额度 |
    74	| `quickSupplemental` | `{}` | 申请补充检查包（RFC §8），条件不满足时返回原因与可申请时间 |
    75	| `continueDeep` | `{ explicitNew: boolean, idempotencyKey }` | 见第 7 节 |

    77	## 5. 追问 `quick_followup`
    78	
    79	- 额度：先在一个短事务里**持久化预留**本次调用（次数、输入上限、输出 512、时长 25 秒，且不超过包内与用户 24 小时剩余额度，RFC §8），再在事务外调用模型，返回后再用短事务核销实际用量。**预留写入失败就不调用模型**；核销失败时保留预留。每一次自动重试都重新预留，并消耗包内共享的那一次重试额度。
    80	- 输入：题目、本题 `subquestions`、当前卡片、本次已有的追问与学生回答；整个请求不超过 4,000 tokens，超出时返回提示、不截断。
    81	- 输出 Schema：`{ question: string /* ≤80 字，以问号结尾 */, targetKey: string | null }`。
    82	- 规则（提示词 + 行为用例 16、17）：只问一个问题；不给论点、例子或结论；可以给思考方向；不评价立场。
    83	
    84	## 6. 检查 `quick_check`
    85	
    86	1. 取卡片版本 v 的不可变快照。同一版本已有实质结果（通过或还需展开）时直接返回该结果，不消耗额度（RFC §8）。
    87	2. 代码从本题 `subquestions` 和 `layout` 生成要求清单：`{ id, zh, keys[] }`。槽位为空的要求直接判为缺，不送模型；全部为空时不调用模型，也不消耗检查次数。
    88	3. 预留额度（输出 768）→ 事务外调用模型 → 输出 Schema：
    89	
    90	   ```ts
    91	   { results: Array<{ id: string; status: "met" | "gap"; note: string | null /* gap 时 ≤60 字 */ }> }
    92	   ```
    93	
    94	4. 校验：覆盖每条送出的要求且没有多余的；`note` 不超过 60 字，且不含 6 个以上连续英文单词（防止写出示范句）。不合格时，若共享重试额度还在就自动重试一次，否则记 `invalid_output`。
    95	5. 提交：在一个短事务里，**只有当前 `content_version` 仍等于 v、练习和账户都还在时**才写入卡片状态、`quick_check_results`、`last_check_id`，以及第一次通过时的 `completion_events`。否则这次操作记为 `stale`，不改卡片（RFC §4）。
    96	6. 规则：只看是否回答了题目的每个要求、有没有相关的理由；不看观点好坏，不打分。
    97	
    98	## 7. 写成作文（RFC §4）
    99	
   100	- `continueDeep { explicitNew: false }`：查 `default_continuations`。已有子练习就返回它（“打开作文”）；已删除或已放弃时返回 `409 default_child_gone`，界面提示需要明确选择“另开一次练习”；没有就在事务里创建 `activity=deep, mode=practice` 的新会话，写入 `continuedFromQuickId` 和卡片快照（`cardSnapshot`：内容、来源、检查状态、版本），并写映射。
   101	- `continueDeep { explicitNew: true }`：按 `idempotencyKey` 去重，创建另一次练习，复制当前卡片快照，不改映射。
   102	- 精练会话的写前与写作阶段，左栏显示 `cardSnapshot`（只读）。之后改动原卡片不影响这份快照。
   103	
   104	## 8. 恢复
   105	
   106	- 服务启动时，把 `quick_operations.status = running` 的记录改为 `indeterminate`，预留额度保持扣除，不自动重发（RFC §8）。界面显示“上次检查没有完成”，提供使用重试额度的按钮；重试读取 `quick_operation_inputs` 中冻结的输入，不用当前卡片代替。
   107	- 刷新或重复点击：同一 `(kind, card_version)` 已在运行时返回运行状态，不新建操作。

   152

   156	
   157	Idempotency is keyed to the logical operation and card contentVersion, not merely the caller's arbitrary request ID.

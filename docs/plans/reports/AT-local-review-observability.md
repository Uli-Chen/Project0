## 保留的限制与发布事项

1. `lib/llm/payloads.ts:4–12` 每次最多清理 500 条，触发点为启动和内容写入。若服务长期空闲或历史积压很大，超过 90 天的物理记录仍可能暂留。发布前必须调整面向用户的承诺或实现可兑现的维护机制；现有接受报告已经保留这一门槛。
2. payload 不存 reasoning_content 和授权头；无可用 message.content 的 HTTP/连接失败记录 `response_text=null`。这降低了完整上游错误诊断能力，但避免将供应商错误对象、潜在账户数据或推理正文持久化。
3. Deep 日配额是旧档位方案内容，不是当前 T1～T6 范围；不要把现有并发限制描述为 Deep 的每日计费硬上限。¥50 限制适用于本评测运行，不能证明供应商账户的其他并发工作也被限制。
4. 本轮采用主agent于2026-11-03核对的官方峰值价：输入2元/百万token、输出8元/百万token，来源为 `https://api-docs.deepseek.com/zh-cn/quick_start/pricing`。本审查未另行联网核价；脚本仍不能鉴别任意来源字符串真实性。后续换价或换模型应重新核对。
5. 静态资源和 API 存储边界测试不能证明模型不会在回复中复述提示词；后者仍需真实对抗评测与语义判定。代码审查不替代 T6b/T6c。
6. 备份和服务器日志保留天数及隐私占位项尚待完成。未设置备份保留天数时不清理，是明确的安全默认值，不应当被报告成已经实施备份到期删除。


## 2026-11-04 预算更新复核

已重新阅读 `evaluationBudget`、fetch 包装器、3-worker 调度及 `tests/tutor-evaluation.test.ts`，未修改脚本，未重新派发模型调用。当前逻辑未发现新的 P0/P1 预算缺口：

- 预留发生在第一个 await 之前，采用整数微元计费；三个并发worker共用同一个账本，因此并发请求不会分别看到同一笔可用余额而超额派发。
- 每个预留的结算闭包只生效一次。响应解析失败、网络中断、缺失或不合法usage都占满该次上界；catch再次结算不会重复收费或返还。
- 输出预算必须等于16,000，整个请求UTF-8字节加320不超过64,000，累计最多432次。每次最坏预留为0.256元；实际usage结算后可继续使用释放的差额。
- 一旦无法预留、总次数耗尽或供应商回报超出声明上限，会停止后续派发；已在途请求仍被原预留覆盖并等待结算。提前停止设置halted或completedRounds不足，退出码2；score额外要求完整live且无halted，partial和mock不能被汇总成通过。
- 测试明确覆盖同步并发预留、预算不足、已知/未知usage、重复结算、次数上限、请求输出及输入体积限制。ALS的每轮context/attempts属于各自任务，worker内多轮按顺序执行；这里是代码审阅，不把旧的218项总通过数冒称成新版脚本的最新回归总数。

只读快照：运行目录 `2026-11-03T15-56-21-279Z` 在本次读取时为live，137次请求、129/216轮、accountedCny=1.60538、reservedCny=0.512、unknownUsage=1、halted=null。这是执行中的瞬时值，不是最终账单或最终验收结果；最终以主agent保存的完成记录为准。

预算保证的前提仍然是供应商遵守请求预算且核对价格适用。若供应商事后回报超限，脚本只能记录并停止后续请求，不能撤销已发生的外部费用。运行之间不共享账本，¥50约束也不覆盖同一账户的其他任务；重跑需单独计入用户授权总预算。

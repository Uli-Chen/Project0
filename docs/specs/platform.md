# 运行支撑、数据和恢复

版本：0.2-draft。维护：AG-PLAN 起草，创始人批准。基线来源：原方案 §5.8～5.9、§6、§7、§10、§12。关联：[ADR-002](../decisions/002-recovery-and-entitlements.md)。

## CORE-001 — 任务可恢复

- 创建提交、评估占位和待调度记录在同一个数据库事务中完成；提交成功后即使队列不可用，调度器仍可重新投递。
- 队列采用至少一次投递，数据库中的任务状态、租约和阶段结果是事实来源；租约过期可被重新领取。
- 默认单次模型调用超时 30 秒；单阶段总尝试上限 3 次（含初始调用、格式修复和供应商重试），退避 1 秒、3 秒并加抖动；任务截止 180 秒。配置随版本记录。
- 自动重试耗尽进入失败状态；可恢复失败允许用户手动恢复最多 2 次，复用逻辑资源与已完成阶段，完整记录尝试；继续失败需运营处理。
- 分数已生成、反馈失败时仅恢复反馈；改写评分已完成、比较失败时仅恢复比较。
- SSE 只通知变化；刷新、断连或事件遗漏后通过 GET 读取完整快照。SSE 读取不创建任务，不触发重复模型调用。
- 支持 event_id 与 Last-Event-ID；事件保留 24 小时，超出窗口通知客户端重新 GET。任务终态不能被迟到 Worker 覆盖。

## CORE-002 — 幂等、额度与成本

写操作使用 Idempotency-Key，按 user_id + 操作类型隔离。数据库唯一约束保证同一操作键只能关联一个请求哈希和逻辑资源；相同内容重放返回既有资源，正文不同时返回 409。键保留至少覆盖闭环生命周期，不仅依赖 Redis 锁。

MVP 提供每个邀请用户一个完整试用闭环；原稿配额仅在合法输入创建成功后占用，系统失败可恢复，确认不可评分则释放该次配额并允许重新提交。改写失败保留其记录并恢复原评估，不因重试扣除新配额。运营重置配额需审计。

本阶段没有用户货币扣款或 LT。每次供应商调用作为独立 attempt 记录 input/output/cached tokens、耗时、价格版本和成本；重试也是真实成本。迟到结果记录 usage，但不得更改已经删除或终态的业务结果。供应商未返回 usage 时标记 unknown，不记作零。

运营报告按 loop_id 汇总全闭环实际成本，包含初稿、仲裁、反馈、Tutor、改写、比较和失败重试。目标 <¥0.50，规划值 ¥0.30；未测量不得当作实际成本。

## CORE-003 — 用户隔离与输入边界

- 全部资源读写、SSE、导出、重试和删除都校验资源所属用户；无权访问统一返回 404，避免枚举。
- 管理重试、版本切换、导出和删除有独立角色与审计；客户端无法提交模型密钥、pipeline 或 Tutor 越级指令生效。
- 按用户和 IP 限流；初始每用户最多 2 个运行中任务、每分钟 10 次写请求，超限 429 且不占用新配额。
- 作文、题目和 Tutor 输入作为不可信数据隔离，响应做 Schema 与证据校验；不赋予模型跨用户读取或任意工具权限。
- 常规日志不记录正文、提示全文或密钥；密钥从运行环境注入。网络通信与存储保护在真实用户试用前落实。

## CORE-004 — 数据生命周期

- 当前默认原稿、改写、草稿及包含原文的反馈/Tutor 记录保留 180 天；删除按关联图覆盖分句、比较片段、缓存、分析副本与导出文件。
- 用户可导出自己的题目引用、两篇作文、反馈、提示和结果；导出链接受鉴权且 24 小时失效。
- 请求删除后立即禁止读取和新任务；活动库、缓存、导出文件 7 天内清理，操作有可查询状态。Worker 回写前检查 tombstone，不能复活数据。
- 本机缓存在线收到删除状态后清理；离线设备无法保证远程即时擦除，恢复登录/联网时校验删除版本后清除，不能重新上传已删除草稿。
- 备份策略在部署时定稿：本阶段要求备份最长 30 天轮换，删除任务在其轮换到期后才标记备份清理完成；恢复备份必须先重放删除清单再开放服务。
- 用量记录仅保留去关联后的运营字段，删除可追溯用户标识；没有支付时不套用交易记录长期留存。去标识不自动等于匿名，导出/日志范围需审查。
- 未单独授权的试用作文不得进入校准或训练集。撤回授权后停止后续使用；已衍生的数据集/模型影响交由单独流程评估并记录。

## CORE-005 — 可观察和可追踪

所有阶段关联 trace_id、loop_id、submission_id、evaluation_id、attempt_id 与 pipeline 版本。结构化事件只记录匿名化业务标识和状态，不复制作文。

最小事件：practice_started、draft_submitted、feedback_viewed、tutor_requested、revision_submitted、comparison_ready、comparison_viewed、loop_completed、task_failed、deletion_requested。每种事件明确客户端还是服务端来源；完成、提交、失败由服务端确认。

`loop_completed` 对 loop_id 唯一。界面重复打开可以产生访问事件，但不能重复计为完成闭环。埋点失败不得阻止保存稿件；由持久化业务事实补写关键事件。

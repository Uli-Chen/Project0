## 1. 一句话与设计原则

**教练是一个有证据记忆、能判断下一步、会逐渐减少帮助的写作陪练。** 它从学生自己的想法出发，用追问把论证推深，用最小修改帮学生把意思写成准确的英文；它记得学生上次卡在哪里，并在下一篇里检验学生是否已经能独立做到。

| 原则 | 含义 |
|---|---|
| 学生的内容 | 立场、理由、例子都来自学生。教练不新增学生没表达过的内容 |
| 下一步优先于讲解 | 每轮只推进一件事；答对就收束，卡住就换方法 |
| 帮助逐渐减少 | 记录每个问题实际给了多少帮助；同一技能下次从更少的帮助开始 |
| 证据记忆 | 教练引用的每条记忆都能指到原句和日期；证据不足就不说“经常” |
| 辅导与评分隔离 | 评分只看题目、冻结稿和评分规则；辅导多少不影响分数 |
| 代码管规则，模型管措辞 | 状态转移、记忆计数、权限、来源校验由代码完成；模型提出教学动作和措辞 |

## 2. 用户需求

目标学生是中国大陆的成年雅思考生，多数目标 6.5～7，常用中文构思，单次约 45 分钟，经常在手机或微信内置浏览器使用。按重要性排序（推测，需要试用观察验证）：

1. **把已有想法展开成有效论证。** 有立场，但理由停在“很好、很重要”，例子空泛，推理跳步。这是 TR 的主要失分点，也是“不给范文”路线最有差异化的地方。速刷检查曾把循环论证判为通过（[WP5_coach_behavior.md](../plans/reports/WP5_coach_behavior.md)）。
2. **知道最值得改哪里，并且真的改得动。** 每篇最多 3 个问题，但应默认只推进一个：定位原句 → 说明影响 → 学生尝试 → 核验是否解决。商业备忘录 §8 把“收到反馈后真的改写”列为核心待验证假设。
3. **把自己的意思准确写成英文。** 要区分“不知道说什么”和“知道意思但不会说”。后者可以直接讲词义、语法并给最小修改，不必反复反问。
4. **确认是否真正进步。** “这篇改好了”“提示后做对了”“新题上独立做对了”是三种不同的结果，要分开记录和展示。
5. **降低开始和坚持的成本。** 允许中文构思、跳过写前、只改一个问题、恢复上次进度；不要求填满提纲才能开始写。
6. **积累自己的素材。** 主题卡片和提纲里的原话可以在相关题目中被想起，但不能替代完整写作。

## 3. “AI native” 在这里指什么

**要做的：教学决策随学生的证据变化。**

- 理解学生刚补充的意思，更新当前缺口，而不是照预设脚本问下一题。
- 学生答对后立即收束；卡住时换一种帮助方式；学生能独立做到时撤掉提示。
- 把写前观点、正文句子、反馈问题、改写结果串起来，知道同一个困难出现在哪一步。
- 下一篇拿出准确的旧证据，在新题上检验能否迁移。
- 学生只需要说话或写作，代码根据状态推荐最可能需要的下一步。

例：学生已经说明两个谓语都对应 This，下一步应该检查改后的动词形式，或者结束这个问题，而不是再让学生找一次主谓（[USER_EXPERIENCE_20261101.md](../plans/reports/USER_EXPERIENCE_20261101.md)）。

**不做的：看起来 AI native，但对提分没有帮助。**

人设与多角色互相讨论；无限自主循环；每句话实时点评；长篇“深度分析”；凭一次改写宣布提分；让学生配置模型档位或回复风格才能得到合适的帮助。

## 4. 角色与边界

对学生只呈现**一个教练**。内部按权限分成三类调用：

| 类别 | 调用 | 能看到 | 不能看到 / 不能做 |
|---|---|---|---|
| 评分诊断 | `evaluate` | 题目、冻结稿、评分规则、分类表 | 记忆、目标分、辅导历史、帮助记录 |
| 对比核验 | `compare`、`review` | 两稿、原问题、句子对应；`review` 另看提纲和本篇重点 | 不读记忆；不因接受过帮助而加分 |
| 教学 | 写前、写中、改写、提醒、总结 | 题目、正文、提纲、教学状态、学习者档案 | 不能改分数；不能把提示后的成功写成独立掌握 |

补充说明：`finish` 现在读取学习者信息和最近 5 篇的问题。它的展示文字属于“教学”，可以调整长度和语气；但进入记忆的事实只来自代码对证据的计算（§9），不来自 `finish` 的自由文字。

**主动与被动的分寸：** 以学生求助为主。自动介入只有段落提醒和开场两种，每篇的有效提醒初值最多 2 次，可忽略、可整篇关闭，模考原稿禁用。系统忙时跳过自动提醒，不排队。

## 5. 现状与差距

| 方面 | 现状（基线 `90f5655`） | 差距 |
|---|---|---|
| 教学准则 | 每个教练任务文件是一小段约束（103～360 字符）；`system/preamble.txt` 只讲语言、安全、JSON | 没有统一红线；各调用点的边界不一致 |
| 多轮连续性 | 主要靠最近 20 / 14 / 8 条消息窗口；另有 `issueLevels`、问题上下文和提纲 | 没有显式的已确认事项和尝试结果，导致重复追问 |
| 学习者信息 | `coached()` 只传目标分、自述难点和 `profile.lang`；`issue`、`nudge` 不传 | 教练每篇都是“第一次见面” |
| 讲解语言 | `profile.lang` 来自问卷的“写作思考语言”（[onboarding-form.tsx:136](../../components/pages/onboarding-form.tsx)），却被当作 `learner.language` 决定讲解语言 | 构思习惯和讲解偏好混在一起 |
| 记忆 | `buildMemory`（[summary.ts:55](../../lib/learning/summary.ts)）按模型自由字符串 `issue.code` 聚合，全部归为 thinking，证据用 `issue.why`，检查次数用全部已评作文数 | 不可靠，不能支撑“反复出现”或“已改善” |
| 分类表 | [taxonomy.ts](../../lib/taxonomy.ts) 只注册、未使用；诊断输出自由字符串；提示词要求最多 3 个问题，schema 允许 5 个 | 部分条目与教学原则冲突（T03、T06、L07，见 §9.4） |
| 写作重点 | `FOCUS_ENABLED` 默认关闭；题库路径 `focus` 恒为 null；旧入口（[route.ts:28](../../app/api/sessions/route.ts)）会赋值 | 重点闭环没有打通 |
| 开场 | 按题型的 5 条固定文字 | 不引用任何个人证据 |
| 提纲提取 | 只校验 `source` 出现在学生原话里（[engine.ts:118](../../lib/pipeline/engine.ts)） | `update.text` 仍可能添意 |
| 可采用文字 | 只有 `polish / check / express` 的建议进入卡片和采用记录（[engine.ts:164](../../lib/pipeline/engine.ts)） | 改写 level 3 的示范句只在回复里，不计入 AI 文字占比 |
| 调用观测 | 精练调用不写 `llm_calls`（只有传 `userId` 时才写，[client.ts:44](../../lib/llm/client.ts)）；已有离线行为评测脚本 | 缺少生产调用级观测，无法可靠归因成本与行为差异 |
| 并发 | 普通精练 action 的会话锁覆盖整个模型等待；`retry-review.ts` 已采用锁内快照、锁外调用、锁内合并 | 自动调用会和保存、显式求助争锁 |

## 6. 能力地图

“现”表示已有，“改”表示改造，“新”表示新增。括号里是所在阶段（§15）。

| 环节 | 触发 | 输入 → 输出 | 硬约束 |
|---|---|---|---|
| 选题〔现〕 | 进入主题页 | 练习事实、题型覆盖 → 一道推荐题及理由 | 代码排序；学生自由选题 |
| 开场〔改，②〕 | 进入写前 | 题型开场 + 至多一条带日期的证据 + 可拒绝的本篇重点（代码拼装，不调模型） | 没有合格证据就省略；模考不显示针对性内容 |
| 写前〔改，①〕 | 学生回答 | 题目要求、提纲、写前线程状态 → 一个教学动作；提纲更新提案 | 只问一个问题；不强求反方、例子或填满所有槽位；不给观点菜单；论证帮助最高 A2（§10.2） |
| 写中〔改，③〕 | 学生提问、选中文字、请求英文表达 | 当前句段、全文、正文线程状态 → 解释 / 追问 / 建议卡片 | 意思不清先澄清；可采用的文字只走建议卡片 |
| 段落提醒〔改，③〕 | 段落完成后停顿 8 秒（现有，[essay-editor.tsx:77](../../components/essay/essay-editor.tsx)）且通过筛选 | 当前段落、本篇重点、已解决事项 → 指出一个缺口或不输出 | 不重复已解决的问题；每篇有效提醒 ≤ 2；忙时跳过 |
| 提交与评分〔现〕 | 学生提交 | 冻结正文 → 分数与问题 | 评分隔离；分类码输出在②接入 |
| 反馈〔改，①〕 | 评分完成 | 全部问题 → 默认展开一个首要问题和一个可执行动作 | 其余问题保持可访问；不把写作偏好包装成评分规则 |
| 改写〔改，①〕 | 学生尝试或请求提示 | 原问题、当前尝试、问题线程状态 → 核验 / 纠正 / 下一级提示 | 答对即收束；A3 / L3 只能一句，并且走建议卡片 |
| 对比〔现〕 | 改写提交 | 两稿、原问题 → 每个问题的解决状态 | 删除问题句不等于学会；没改善如实显示 |
| 总结〔改，②〕 | 结束练习 | 本次证据 → 做到了什么、还要练什么、下次验证什么（默认三条） | 展示文字不直接写入记忆 |
| 下一篇〔新，②〕 | 新练习 | 学习者档案 → 开场与本篇重点 | 最多引用一条证据；学生可以拒绝重点 |
| 速刷〔现〕 | 卡片追问、检查 | 卡片原文、题目全部要求、最近回答 → 一个追问或缺口 | 保留现有额度、关闭思考和独立 schema；接入共享准则作为独立变更验收 |
| 卡片复习〔新，③〕 | 学生在复习页发起 | 隐藏卡片内容 → 学生先回忆，再与原卡比较遗漏 | 不生成卡片答案 |

## 7. 交互形态

在 [coach-tab.tsx](../../components/essay/coach-tab.tsx) 现有的共享输入框（提问 / 试写 / 英文怎么说、引用标签、问题上下文）基础上渐进改造：

1. **共享输入框 + 推荐下一步。** 代码根据阶段和教学状态，在输入框旁推荐 1～3 个动作，例如“我试着改一下”“再给点提示”“展开讲讲”“检查我的改写”。
2. **“更多工具”保留稳定入口。** 理清、润色、检查、英文表达等工具不会因为状态变化而消失，解决可发现性问题。手机端减少常驻控件，但不能只靠长按选文才能发现工具。
3. **引用、当前问题和表达模式保持可见、可移除。**
4. **`move` 只表示教练本轮的教学动作**，不同时承担学生意图、接口 action 和阶段转换。自由提问可以在同一次调用里选择追问、解释或核验，含糊时先澄清。提交、结束、采用建议，以及进入会给出可采用文字的模式，仍需要学生明确操作。
5. **可采用文字只走建议卡片。** 任何会被写入正文的文字，都必须经过建议卡片、采用记录和 AI 文字占比的链路，不能藏在回复里。第一阶段先覆盖改写的示范句，第三阶段覆盖所有教练调用。AI 文字占比仍只是站内采用估计，不代表帮助程度或思想归属。
6. **“展开讲讲”取代三种风格。** 默认回复短；学生点“展开讲讲”后，同一个教学动作再讲一遍理由和自检方法，不改变帮助级别，也不提前给出下一级提示。

## 8. 教学状态与学习者档案

### 8.1 数据结构

```ts
type Ref = {
  sessionId: string;
  kind: "message" | "essay" | "outline" | "card" | "evaluation" | "profile";
  id: string;
  version: string;   // 不可变版本或内容哈希
  quote: string;     // 来源原话
  at: string;        // 来源日期，由代码填写
};
type Skill = { code: TaxonomyCode; taxonomyVersion: string };
type HelpTrack = "argument" | "language";   // 两套阶梯，见 §10.2
type Help = 0 | 1 | 2 | 3;
type Move =
  | "ask" | "clarify" | "explain" | "hint" | "check_attempt"
  | "confirm" | "suggest" | "invite_write" | "point_gap" | "summarize" | "noop";

/** 一条教学线程：写前、正文、或某个反馈问题各一条 */
type TeachingState = {
  v: 1;
  status: "open" | "closed";
  closedReason: "met" | "student_left" | "switched" | null;
  current: { id: string; target: string; skill: Skill | null; track: HelpTrack; refs: Ref[] } | null;
  openQuestion: { text: string; askedMessageId: string } | null;
  established: { id: string; text: string; refs: Ref[]; basis: "student_stated" | "student_confirmed"; retracted: boolean }[];  // 有效项 ≤ 8
  attempts: { messageId: string; refs: Ref[]; result: "unchecked" | "met" | "partial" | "not_met" | "unclear"; reason: string; help: Help }[];  // ≤ 3
  allowedHelp: Help;      // 本线程目前允许的帮助上限（权限）
  providedHelp: Help;     // 实际已经给出的最高帮助
  legacyLevel: 1 | 2 | 3 | null;   // 旧会话的 issueLevels；实际帮助未知
  next: { move: Move; target: string } | null;
};

/** 会话创建时由代码冻结的跨练习上下文（第二阶段） */
type LearnerBrief = {
  v: 1;
  frozenAt: string;
  focus: { value: Focus; skill: Skill | null; origin: "student" | "evidence" | "legacy"; refs: Ref[] } | null;
  difficulties: { skill: Skill | null; text: string; basis: "self_report" | "observed_once" | "recurring" | "improving"; refs: Ref[] }[];  // ≤ 2
  material: { text: string; refs: Ref[] } | null;     // ≤ 1，与本题话题相关的学生原话或卡片
  lastPractice: { text: string; refs: Ref[] } | null;
  explainLanguage: "zh" | "en";
};

type TutorState = {
  v: 1;
  brief: LearnerBrief | null;
  activeThread: string | null;          // "prewrite" | "body" | "issue:<rank>"
  threads: Record<string, TeachingState>;
};
// SessionState.tutor?: TutorState —— 随 state_json 保存
```

### 8.2 统一输出与状态增量

教学调用的输出为 `{ move, reply, delta, payload }`：

- **`payload`** 按 move 区分。只有 `suggest` 允许建议结构；写前的提纲更新 `outlineUpdates[]` 可以和写前允许的任何 move 共存。速刷继续使用自己的 schema。
- **`delta`** 是增量操作列表，模型不能覆盖整个状态。允许的操作：

| 操作 | 作用 | 代码校验 |
|---|---|---|
| `establish { text, refKey }` | 记下学生说过或确认过的一件事 | `refKey` 必须是本次提供的学生消息引用；第一阶段 `text` 必须是该消息的连续原话片段；`basis` 由代码判定，模型推断不能进入 |
| `retract { establishedId, refKey }` | 学生纠正了之前确认的事 | 必须引用学生的纠正原话；原项标记 `retracted`，不删除 |
| `ask { text }` / `clearQuestion` | 设置或清除开放问题 | `ask` 与 move 一致；写前和速刷要求只有一个问题 |
| `recordAttempt { refKey, result, reason }` | 核验学生的一次尝试 | 只有 `check_attempt` 能写；同一条学生消息只记一次 |
| `close { reason }` | 结束线程 | `met` 需要本轮 `check_attempt` 的核验结果为 `met`；`confirm` 只做局部确认，不能关闭线程 |

- **帮助级别：模型声明，代码限权。** 仅凭 move 和 payload，代码无法确定性地区分相邻级别（例如 A1 与 A2），所以由模型在输出中声明本轮的 `help.level`。代码保证它不超过 `allowedHelp`，`suggest` 固定为最高级；`providedHelp` 取历史最高值。声明是否属实，由行为评测抽查（§12）。
- **线程重开：** 学生回到已结束的问题时，同一线程重新打开，保留已确认事项和帮助记录。已结束的线程不进入其他线程的调用上下文。

各环节允许的 move（仍受显式 action 和帮助上限约束）：

| 环节 | 允许的 move |
|---|---|
| 写前 | ask、clarify、explain、hint、confirm、invite_write |
| 写中 / 改写 | ask、clarify、explain、hint、check_attempt、confirm、suggest |
| 反馈问题讨论 | 同上；suggest 只在帮助上限达到 3 时 |
| 段落提醒 | point_gap、noop |
| 总结 | summarize |
| 评分 / 对比 / 模考原稿 | 不进入教练协议 |

`confirm` 只确认局部判断，不宣布掌握。

### 8.3 校验与失败语义

- **后置校验放进 schema。** 每次调用由代码按本次上下文生成 Zod schema：允许的 move 集合、合法的引用键、帮助上限、数量上限都写成 refine。这样不合格的输出会走 `generateJson` 现有的解析失败重试路径（[client.ts](../../lib/llm/client.ts) 只对解析和格式错误重试）。
- **回复和状态一起接受或一起拒绝。** 任何一项硬校验失败都视为整次输出无效，不允许“保留回复、丢弃部分 delta”。
- **重试用尽：** 不保存回复，不改状态，不增加帮助级别，不记尝试；保留学生的文字，提示重试。
- **晚到结果：** 返回时如果正文版本、线程或引用的来源已经变化（包括学生删除了记忆），整次结果作废，提示重新请求。
- **原话匹配的边界：** 它只能证明“这句话学生说过”，不能证明模型的归纳成立。

### 8.4 裁剪、兼容与删除

- 每个线程的有效确认项 ≤ 8、尝试 ≤ 3、开放问题 1 个。第一阶段确认项超出上限时按先进先出归档，归档项不进入调用上下文，不判定、也不承诺保留“关键项”（v1.3）；是否需要关键项判定，看评测中长对话用例的结果。
- 旧会话缺少 `tutor` 字段时视为 `null`：下一次真实交互时初始化当前线程，不伪造“创建时已有的 Brief”。旧的 `issueLevels` 写入 `legacyLevel`，实际帮助记为未知。沿用 [read-session.ts](../../lib/pipeline/read-session.ts) 保留未知字段的策略，只校验新子树。
- `LearnerBrief` 由代码在会话创建时生成并冻结，模型不能写。冻结不豁免删除：每次组装上下文和保存晚到结果之前，过滤已被学生删除或纠正的来源。

## 9. 学习者模型与记忆

### 9.1 四层信息

| 层 | 内容 | 来源 | 说明 |
|---|---|---|---|
| 用户声明 | 目标、考试时间、可用时间、写作思考语言、讲解语言、自述难点 | profile | 自述水平不当作测量结果；讲解语言是新的独立字段（§9.5） |
| 当前教学状态 | 当前问题、已确认事项、最近尝试、帮助级别 | `tutor.threads` | 防重复的最小核心 |
| 跨练习证据 | 分类码、作文版本、原句、日期、是否新题、帮助事件、评估版本 | 评估结果 + 代码 | 只用原稿计数 |
| 学生素材 | 卡片、提纲原话 | 卡片、outline sources | 旧观点只供参考，不代表学生的永久立场 |

### 9.2 帮助事件

判断“独立表现”的前提，是知道学生在这一稿上得到过哪些帮助。

- **帮助事件**按正文版本记录，覆盖所有教学入口：写前、写中、提醒、改写。每条记录来源入口、实际帮助级别、涉及的技能（可以为空）。无法判定的记为 `unknown`。
- 没采用的建议也算得到了帮助；提前告诉学生本篇重点，本身也是一种提示。
- 三种结果分开记，只有最后一种叫“独立迁移”：

| 结果 | 条件 |
|---|---|
| 知道重点后做到 | 本篇重点是该技能，学生事先知道，没有针对该技能的其他帮助 |
| 针对性辅导后做到 | 本稿有涉及该技能的帮助事件（包括改写阶段） |
| 未提示的新题迁移 | 新题原稿，没有预告该技能，也没有涉及它的帮助事件，核验达成 |

- 第一阶段只记录原始帮助事件，技能归因可以在第二阶段补上。

### 9.3 状态规则（初值，待用数据校准）

- **代码**负责去重、来源匹配、题目家族、计数、删除排除、状态转移和相关性筛选。**模型**只提出带来源的语义观察，不能宣布长期掌握。
- **没出现 ≠ 已通过。** 一篇最多报告 3 个问题，某个问题没被报告，只表示“未报告”，不计入分母。
- 状态从剩余证据**重新计算**（纯函数），不存增量状态。学生删除某条证据后，下次读取时自动重算。
- 状态只用三种，**第一版不引入长期 `resolved`**：

| 状态 | 条件 |
|---|---|
| `observed_once` | 只有 1 篇原稿出现该技能问题（同一题目家族只计一次） |
| `recurring` | 最近 3 篇有该技能核验结果的原稿中，有 ≥ 2 篇出现 |
| `improving` | 该技能最近 2 篇有专门核验（`focusResult`）的新题原稿都达成，并且其中至少 1 篇属于“未提示的新题迁移”或“知道重点后做到” |

- 一次达成最多支持“这一篇做到了”。`comparison.issues[].status = resolved` 只表示“这一稿里这个问题解决了”，两者不能混用。
- `finish.memoryChanges` 现阶段只当作展示文字，不当作记忆事实。

### 9.4 分类表 v2 与写作重点

- **先修分类表，再接入诊断。** 现有 [taxonomy.ts](../../lib/taxonomy.ts) 有几处与教学原则冲突：T03 要求每个主体段都有例子；T06 要求回应反方；L07 限制连接词次数。这些是写作偏好，不是评分要求。修订后升级 `taxonomyVersion`。
- **诊断直接输出版本化分类码。** 这样少一次调用、少一种失败状态，也避免诊断和归类不一致，并且符合 [原型/12 §5.3](../../原型/12_题库与推荐.md) 的打开前提。允许“未归类”，不强行塞给最接近的码。旧的自由字符串不追认为有效分类码。
- **这是批改配置变更**，按风格档位 RFC §8 处理：新版诊断先离线校准，用冻结作文比较各维分数、问题覆盖和分类一致性。**校准失败时保留旧 `evaluate` 配置，新分类结果不进入正式评分、记忆或重点。**通过后再升级 `judge_version` 并启用。不能声称“只加了字段，所以分数不变”。如果要把 schema 的问题上限从 5 收紧到 3，也一起纳入这次校准。
- **校准集（owner 决定，2026-11-03）：** 正式校准作文和参考分暂时留空，以后补充。在此之前，可以用少量 toy example 搭建和调试校准工具、分类码解析和记忆重算。toy example 只能证明流程能跑通，**不能作为校准通过的依据**：正式校准集到位并通过之前，新版诊断不在生产环境启用，自动重点保持关闭。这不阻塞第一阶段。
- `focusResult` 扩展为 `{ achieved: "yes" | "partial" | "no" | "no_opportunity" | "unclear", note, refs }`，记录核验范围和原句证据。
- **重点闭环**分两步接入：
  - 第二阶段：开场提出（可拒绝）→ 提交后 `review` 核验 → 总结说明结果 → 下一篇决定继续还是换。
  - 第三阶段：写中提醒围绕重点。不做提交前自检（owner 决定，2026-11-03）。
- 自动选重点需要至少两篇合格的新题原稿证据（原型/12 §5.3）。

### 9.5 讲解语言与学习偏好（owner 决定，2026-11-03）

- 新增独立字段 `explainLanguage: "en" | "zh"`，**默认英文**。所有缺少该字段的账户（包括现有账户）都按英文讲解；`profile.lang` 只表示写作思考语言，不再影响讲解语言。
- 讲解语言、写作思考语言、段落提醒开关等学习偏好**统一放在用户中心**。问卷不再单独设置讲解语言。
- 修改后从下一次教练请求开始生效，进行中的请求不变。
- 适用范围：第一阶段只覆盖精练的教学调用。速刷追问（提示词要求中文）和评分反馈（`evaluate` 要求中文理由与提示）保持中文不变，因为两者都属于固定基线；评分反馈是否跟随讲解语言属于批改配置变更，放到第二阶段和分类码一起校准。
- 上线时，在教练面板第一次出现英文讲解时提示一次“可在用户中心改为中文讲解”（建议，非 owner 原话）。

## 10. 教学准则

### 10.1 统一准则

| 编号 | 准则 |
|---|---|
| G1 | 不新增学生没表达过的立场、理由、例子、数据，也不给观点菜单（对应风格档位 RFC 的 C1～C3、C5） |
| G2 | 语言知识可以直接解释；涉及构思时，引导学生自己生成内容 |
| G3 | 每轮只做一个主要教学动作；答对就不再追问同一点，没懂不能假装通过 |
| G4 | 只在明确的任务里给句子级修改（润色、英文表达、语法检查、改写最高级），不给整段、范文或模板（对应 C4） |
| G5 | 不把反方段、高级词替换、观点新奇等写作偏好当作评分要求 |
| G6 | 每条记忆和进步判断都能追溯到证据；证据不足要明说 |

**放置位置：** 共享的教练准则层（风格档位 RFC §6.1 的 L0/L1），任务层定义例外，“展开讲讲”放在最低层。
**适用范围：** 第一阶段只用于精练的教学调用（写前、写中、改写、提醒）；评分、对比、`finish` 和速刷的请求保持基线不变。速刷和总结接入共享准则，分别作为独立变更验收。

### 10.2 两套帮助阶梯

论证问题和语言问题的帮助方式不同，分开定义。数字表示帮助上限（权限），不要求每轮都用到上限。

**论证类（A，适用于写前和 TR/CC 类问题）**

| 级别 | 内容 | 写前 | 改写 |
|---|---|---|---|
| A0 | 开放问题，指出缺口在哪里 | ✓ 起点 | — |
| A1 | 说出推理类型：原因、后果、对比、亲身观察 | ✓ | ✓ 起点（对应现 level 1） |
| A2 | 与题目内容无关的通用思考维度（谁受影响、短期与长期、程度、和什么比），或推理路线 | ✓ 上限 | ✓（对应现 level 2） |
| A3 | 用学生自己的内容示范一句，走建议卡片 | ✗ | ✓（对应现 level 3），只能一句 |

**语言类（L，适用于 LR/GRA 类问题和写中的语言求助）**

| 级别 | 内容 |
|---|---|
| L0 | 指出位置和问题类型（“这句的动词形式再看看”） |
| L1 | 讲规则或词义 |
| L2 | 给出改法方向（“主语是单数”“这里需要被动”） |
| L3 | 给出改正后的句子，走建议卡片 |

**级别转移：**

| 学生操作 | `allowedHelp` 的变化 |
|---|---|
| “再给点提示”（`more`） | +1，到上限为止。改写从 A1 开始，所以和现在一样点两次到示范句 |
| 提问（`ask`）、试写（`attempt`） | 不变 |
| 尝试核验为 `met` | 线程结束 |
| 连续两次卡住 | 不变；教练换一种方法（比如从问原因改成问亲身经历），不自动升级 |

### 10.3 方向提示的边界（负责人按 owner 授权决定，2026-11-03）

**判定规则：教练不首次引入内容。** 一句提示是否越界，只看它有没有带进学生还没说过的**题目内容**：立场、理由、后果、受影响的具体人群或领域、例子、数据。逐条规则：

1. **可以说的：** 推理的类型（原因、后果、对比、亲身观察）；与任何题目都通用的思考维度（谁受影响、短期与长期、程度、和什么比）；学生自己已经说过的内容。
2. **不能说的：** 和本题内容相关的角度（经济、环境、文化、健康等领域词），任何具体的因果链，任何让学生“选一个”的观点清单。
3. **学生已经提出的角度可以追问。** 学生说过“会更环保”，教练可以问“为什么会更环保”“对谁更环保”；教练不能补上学生没说的“还会减少拥堵”。
4. **问经历不能预设答案。** “你有什么经历”可以；“你有没有因为票价太贵而放弃乘车”把理由塞进了问题，越界。
5. **学生直接要理由时**（“给我一个理由吧”）：用一句话说明为什么教练不替学生想理由，然后在当前帮助上限内换一种提示，不因为学生要求就给内容。点“再给点提示”只会升级到更高一级的方法提示：写前最高 A2；改写最高 A3，也只是用学生自己的内容示范一句。
6. **题型要求不算内容。** 指出“这道题要回答两个问题，第二个还没回答”是允许的，它来自题目本身，不是教练的观点。
7. **拿不准时按越界处理。** 评测里判为越界的样例加入回归集。

**论证类正反例**（题目：政府是否应该让公共交通免费？假定学生还没提出相关内容）：

| 允许 | 越界 | 依据 |
|---|---|---|
| “你倾向同意还是反对？是什么让你这样判断？” | “可以从经济和环境两个方面考虑。” | 规则 2：领域角度 |
| “你亲身乘坐公共交通时，有什么经历影响了你的判断？” | “你有没有因为票价太贵而放弃乘车？” | 规则 4：问题里预设了理由 |
| “先选一种推理：解释原因，还是说明后果？” | “免费会让更多人放弃开车，你能解释为什么吗？” | 规则 2：给出了因果链 |
| 卡住后：“试着比较短期和长期，哪一种更容易想到？” | “短期财政负担会增加，长期能减少污染，你更看重哪个？” | 规则 2：观点清单 |
| 学生说过“会更环保”后：“为什么免费会更环保？” | 学生说过“会更环保”后：“除了环保，还能减少拥堵。” | 规则 3：补上了新理由 |
| 学生要理由：“理由要来自你自己，这样考试时才写得出来。想想：如果车票免费，你自己的出行会有什么变化？” | 学生要理由：“好吧，比如可以帮助低收入家庭。” | 规则 5 |
| 双问题题：“题目还问了政府该怎么做，这部分你还没写。” | 双问题题：“第二问可以写政府增加补贴。” | 规则 6 |

**语言类正反例**（学生原句：*Studying science seem difficult for many students.*）：

| 级别 | 允许 | 越界 |
|---|---|---|
| L0 | “这句的动词形式再看一下。” | 直接给出改好的句子 |
| L1 | “主语是动名词短语时，动词按单数处理。” | 顺便替学生改写整句的表达 |
| L2 | “主语 *Studying science* 是单数，*seem* 要随之变化。” | 同时指出并改正句子里其他未被询问的问题 |
| L3 | 建议卡片：*Studying science seems difficult for many students.* | 给出意思不同的“更好”的句子，或一次给两个版本 |

### 10.4 代码兜底：硬校验与告警

| 类型 | 内容 | 不合格时 |
|---|---|---|
| 硬校验 | JSON 结构、move 是否在允许集合、帮助上限、引用键归属、建议的选中文字匹配、长度上限、模考禁用 | 整次输出无效，走既有重试（§8.3） |
| 硬校验 | 写前提纲更新：`source` 必须是学生原话，否则丢弃该条；`text` 不是学生原话的连续片段时，改用已校验的 `source` 写入槽位（v1.3 起，取代“改述要学生确认”） | 回复照常显示，替换和丢弃都记告警 |
| 硬校验 | 速刷已有的“恰好一个问号、≤ 80 字” | 保持现状 |
| 告警 | 精练回复的问号数量、回复中英文完整句与学生原文的重合度 | 写入调用记录，进入评测抽查，不重试 |

告警不能当作安全保证：它识别不了添意，合法翻译的重合度可能很低，越界论点的重合度也可能很高。

## 11. 架构

### 11.1 一次交互一次主要调用

```text
事件 → 代码准入 → 上下文组装（白名单投影） → 模型提出教学动作 → 校验 → 保存 → 展示
```

- 不做规划器、多代理或向量库。将来确实需要工具时，只开放只读的“取证据原文”“取相关卡片”，限制调用次数；模型不能写数据库。
- **统一上下文构建器**按调用点白名单投影：必须保留当前问题、最新回答、原文锚点和已确认事项，旧的闲聊可以裁剪。消息窗口不再单独承担连续性。
- **投影规则沿用风格档位 RFC §4.3 和开发方案 LG-06：** 保留基线已有的字段、顺序和 ID；新增内容（教学状态、引用键、帮助级别）只能经白名单进入；调用 ID、配置版本、档位和评分来源不进入请求。

### 11.2 并发与锁

- 保留现有会话锁、草稿版本检查和请求幂等；保留单 Node 进程、每用户 1 个模型工作流、全局 8 个的准入。
- 第一阶段不增加自动调用。显式操作优先；自动提醒在系统忙时跳过。
- 第三阶段把自动提醒改成和 `retry-review.ts` 一样的模式：锁内冻结输入 → 锁外生成 → 锁内校验正文版本与生命周期后合并。过期的提醒或建议丢弃，不能覆盖新稿。

### 11.3 成本、延迟与可观测性

- 沿用现有 DeepSeek 配置建立基线；先测各环节的延迟、token、重试次数和整篇练习成本，再调整上限。不靠提高推理预算来弥补上下文缺失。
- 调用记录：每次实际 provider 尝试一条记录，包括调用点、模型、提示词 / schema / 参数版本。另外记录教学动作、帮助级别、引用的证据，以及学生后续的反应（采用、忽略、重复追问、下一次尝试结果）。不保存隐藏推理。
- 不做学生档位 UI，但必须记录每次调用的配置快照，否则以后无法解释行为差异。

## 12. 质量保证

### 12.1 行为评测集

- 目标规模 60 个场景：40 个开发用，20 个封存。每个跑 3 次，至少一半是多轮对话。第一阶段先做其中 30 个关键场景。
- 覆盖：五种题型；学生已答对；反复不会；改变立场；纠正之前说过的话；循环论证；普通但正确的表达；诱导代写（“给我一个理由吧”）；错误或已删除的记忆；上下文截断；英文讲解偏好；论证和语言两套阶梯的各级；藏在学生文字里的指令；天然容易列出角度的话题。

## 13. 指标

| 北极星 | 独立迁移 | 在“未提示的新题”原稿和模考检查点上，学生的重点技能问题是否减少。试用阶段只做描述，不下结论 |

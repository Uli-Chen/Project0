# 文档、任务与变更工作流

角色代号与权限见 [团队与组织](organization.md)。下文“创始人”是唯一审批人；Agent 只在被分配的角色和任务内工作。

## 权威来源

| 内容 | 唯一维护位置 |
|---|---|
| 当前预期行为 | `docs/specs/` |
| 实现状态、执行角色、阻塞、待决事项、PR 与证据链接 | `docs/tracking/tasks.md` |
| 验收结果 | `docs/validation/acceptance.md` |
| 测量细节 | `docs/validation/runs/` 中的报告，或有访问权限的报告链接 |
| 决策理由与替代方案 | `docs/decisions/` |
| 每周进展与调整 | `docs/tracking/reviews.md` |
| 历史原方案 | `docs/baselines/v0.1/`，只读 |

规格引用任务编号；任务引用规格和验收编号。不要在多个看板复制任务状态。以后接入外部任务系统时，先指定新的唯一状态来源，再把本地台账改为索引，避免双向手工维护。

## 就绪条件

任务由 `backlog` 转为 `ready` 前须同时满足，由创始人确认：

1. 依赖任务均为 `done`。
2. 关联需求的规格中没有“待定”“由实现决定”而未指派决策任务的行为；阻塞它的 [待决事项](tracking/tasks.md#待决事项) 已关闭。
3. 任务卡写明交付物、关联验收编号和完成定义；跨任务验收写明本任务负责的检查点。
4. 所需外部资源（签约专家、样本、密钥、环境）已到位，或任务卡写明哪些子项可以先做。

## 开始与完成一个任务

| 步骤 | 执行 | 结果 |
|---|---|---|
| 1. 开始 | 创始人 | 任务改为 `in_progress`；检查在制品上限 |
| 2. 实现 | AG-DEV | 分支名含任务编号，如 `feat/MVP-003-draft-editor`；一个 PR 只做一个可验证子项，附测试命令与结果 |
| 3. 评审 | AG-REV（新会话） | 对照规格、契约和安全要求给出意见；AG-DEV 修改 |
| 4. 合并 | 创始人 | 抽查评审意见后合并；任务改为 `review` |
| 5. 验证 | AG-QA 或 AG-EVAL（新会话） | 按验收清单执行，写验证报告，提出 `passed`／`failed`／`inconclusive` |
| 6. 确认 | 创始人 | 查看或重跑证据后更新验收结果；关联验收有证据后任务改为 `done` |

未达到质量目标的功能可以实现完成，但验证状态必须保持 `failed` 或 `not_run`，不能据此放行。验证中发现的缺陷退回 AG-DEV，在新 PR 修复，不由验证会话直接改产品代码。

实现状态：`backlog`、`ready`、`in_progress`、`review`、`done`、`blocked`、`deferred`。

验证状态：`not_run`、`running`、`passed`、`failed`、`inconclusive`。每个任务明确验证的是契约、功能、质量或试用结论；试用报告完成可以通过流程验收，其学习效果仍可能不确定。

`blocked` 必须写明阻塞原因、解除动作和负责人。`deferred` 必须关联范围决策。没有数据时填写“未测”，不填 0 或估算值冒充结果。

## Agent 遇到不确定时

规格缺失、互相矛盾、需要越过任务边界、需要真实数据或生产凭据、或需要放宽验收数值时，Agent 停止该子项，在 PR 或任务卡写明问题、可选方案与建议，并在台账新增或引用待决事项。不得以“合理假设”继续实现后再补规格。

## 变更分级

| 级别 | 例子 | 谁可以做 | 记录 |
|---|---|---|---|
| 1 文案与说明 | 错字、链接、补充示例，不改变行为 | Agent 直接在 PR 中修改 | PR 描述 |
| 2 规格细化 | 补充边界情况、错误码、界面状态，不改变范围或数值门槛 | AG-PLAN 起草，创始人批准 | 规格修订＋CHANGELOG |
| 3 范围与门槛 | 增删需求、改变验收数值、改变数据语义、评分解释、权益或架构边界 | 仅创始人决定 | 新 ADR＋同步路线图、规格、任务、验收 |

任何新增需求分配稳定编号；已删除编号保留墓碑说明，不复用。影响数据时补迁移与回滚说明。旧 ADR 不重写历史，新增记录并在旧记录中标注替代关系。测试失败后不得通过降低门槛来让它通过；改门槛属于第 3 级，需先有 ADR。

## 每周检查与调整

每周一次，AG-PLAN 先根据台账、PR 和验证报告起草，创始人审阅后写入 [周检记录](tracking/reviews.md)：

- 本周合并与验收变化，用任务和验收编号表示；
- 一个能运行的用户流程演示及其限制；
- 新增或仍未解除的阻塞和待决事项；
- 在制品与评审排队是否超过上限；
- 质量、成本、延迟的已测数据（未测写“未测”）；
- 下周要转为 `ready` 的任务和需要创始人做的决定。

每个切片结束时追加一次切片复盘，按 [路线图](roadmap.md) 的放行条件逐条判断：通过、带条件通过（写明条件与期限）、或不通过（写明退回的任务）。不以文档页数或完成任务数量代替产品进展。

## 验证报告

复制 [报告模板](validation/runs/TEMPLATE.md)，记录日期、执行角色、commit、pipeline、数据集版本、执行命令、结果、限制和证据链接。报告不得包含真实作文、访问令牌或可识别的用户信息。私有样本放在受控存储，Git 只存匿名引用和数据集哈希。

执行 `python3 scripts/check_docs.py`。这是文档结构检查，功能验收仍需按清单执行。

## Git 与基线

当前已初始化本地 Git，没有远程仓库。建议首个文档评审通过后提交当前文件，再由创始人创建 `docs-v0.1-baseline` 标签指向包含冻结快照的提交；不要把它命名为产品发布标签。快照校验值独立于 Git，禁止通过重算 manifest 掩盖历史文件更改。`main` 只接受创始人合并。

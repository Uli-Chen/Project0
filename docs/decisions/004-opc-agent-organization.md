# ADR-004：一人公司＋多 Agent 的组织方式

- 日期：2026-10-23
- 状态：当前采用
- 关联需求与任务：全部 MVP 任务的执行与审批；AC-008、AC-009、AC-017、AC-018、AC-019 的人工部分

## 背景与证据

冻结基线商业计划书第九章按传统创业团队规划 2027 年 6 人、2031 年 24 人，任务台账的负责人列也按人类岗位写成“待认领”。实际运营主体是台湾登记的一人公司，开发、评审、验证由创始人指挥多个 AI Agent 完成。旧写法会让任务永远“待认领”，也无法说明谁有权合并、放行和接触用户数据。

## 决定

- 创始人是唯一的人类成员和唯一审批人，负责合并、放行、确认验收、生产凭据、真实用户数据与对外沟通。
- 设立六个 Agent 角色（AG-PLAN、AG-DEV、AG-REV、AG-QA、AG-EVAL、AG-OPS），每个会话只承担一个角色和一个任务；实现与验证由不同角色、不同会话完成。
- 专家评分、反馈准确性抽检、试用访谈与法律意见由签约人员或创始人完成，不以模型互评作为验收证据。
- 任务台账改为“执行角色／审批人”，由检查脚本校验角色代号。
- 以在制品上限、PR 粒度和每周检查控制创始人评审负载。

详细内容见 [团队与组织](../organization.md)。

## 替代方案与取舍

- 招聘小团队：符合原计划，但与实际资金和运营方式不符。
- 单个通用 Agent 全包：管理最简单，但作者自评自审，验收证据可信度低。
- 角色更细（前端、后端、安全各一个）：分工更清楚，但会增加创始人的交接和评审开销；目前用 AG-DEV 与 AG-REV 覆盖。

代价：创始人是单点，评审速度限制交付速度；试用期间只能提供有限支持时段；Agent 费用成为主要研发支出。

## 影响

- 文档：总览、路线图、工作流、任务台账、试用与评测协议中的负责人改为创始人与 Agent 角色。
- 检查：`scripts/check_docs.py` 校验执行角色代号；台账不再使用“待认领”。
- 财务：原营收模型的人力成本与融资用途失效，需单独重新建模；本 ADR 不更新这些数字。
- 无产品接口或数据迁移影响。

## 重新评估条件

满足 [扩张规则](../organization.md#扩张规则) 中任一信号持续出现；或创始人评审排队连续两周超过在制品上限；或试用支持无法按承诺时限响应。

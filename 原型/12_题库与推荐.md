## 2. 题库导入

- 来源：`data/question-bank/question_bank.mock.json`（`bankVersion = mock-20261101-v1`，38 题）。这份文件已冻结，**不得修改**；它的校验脚本是 `data/question-bank/validate_bank.py`。
- 每题的作答要求另放 `data/question-bank/requirements.mock.json`（第 2.2 节），按 `id + version` 对应。
- 导入脚本 `scripts/import-questions.ts`（`npm run db:import-questions`）：读取两份文件，校验字段与对应关系，按 `(id, version)` 幂等写入 `questions`；同时写入版本化的别名表（第 2.3 节）。导入不调用模型、不联网。
- 题目详情显示 mock 标记：`source.kind` 不是官方真题时显示“练习题（非官方真题）”；不得把任何题宣称为官方真题（RFC §2）。

### 2.1 `questions` 表

| 列 | 来源 |
|---|---|
| `id`、`version` | 主键 `(id, version)` |
| `exposure_key` | 题目家族 |
| `bank_order` | 在当前版本中唯一（部分唯一索引，条件 `is_current = 1`）；所有“按题库顺序”的打平都用它 |
| `text`、`primary_topic`、`secondary_topics_json`、`question_type`、`pool`（`practice` / `checkpoint_reserved`）、`source_json` | 原样 |
| `requirements_json` | 来自 requirements 文件 |
| `bank_version` | 目录版本 |
| `is_current` | 每个 `id` 只有一个当前版本（部分唯一索引 `(id) WHERE is_current = 1`） |

导入时，同一 `(id, version)` 已存在但内容不同（题干、标签、池、家族、`requirements_json` 任一不同）时报错退出，不覆盖已冻结的版本。

### 2.2 每题的作答要求（`requirements.mock.json`）

题型只决定卡片的大致布局；检查时以本题自己的要求为准（评审意见：原因与对策题若只看题型，会放过没回答“原因”的卡片）。

```ts
type QuestionRequirements = {
  id: string; version: number;
  subquestions: Array<{ key: string; en: string; zh: string }>;   // 题目实际要回答的问题，按题干顺序
  layout: "position_reasons" | "both_views_opinion" | "weigh" | "problem_solution" | "two_questions";
  requiresOverallJudgement: boolean;   // 如 outweigh 题必须给出权衡结论
};
```

- `requiresOverallJudgement`：题目明确要求作者给出自己的立场、评价、权衡或优先判断时为 `true`（agree/disagree 的立场、讨论双方后的意见、outweigh 的结论、positive/negative 的评价、“最有效”“是否更重要”的判断）；只问原因、影响或一般措施时为 `false`。按题干判断，不由题型推导。（负责人 2026-11-01 定）

- 由实现者按 38 道题逐题编写，负责人逐题审阅后才能导入；导入脚本校验每道当前题都有一条要求记录。
- 这是内容文件，不是运行时解析：不写任何“从题干里拆问句”的启发式代码。

### 2.3 别名

两张表：

| 表 | 列 |
|---|---|
| `question_aliases` | `alias_version`、`kind`（`legacy_id` / `text`）、`alias`（旧 ID，或 Unicode NFKC + 转小写 + 合并空白后的文字）、`status`（`matched` / `not_in_catalog` / `ambiguous`）、`exposure_key`（仅 `matched`）、`reviewed_by`、`note`；唯一 `(alias_version, kind, alias)` |
| `question_alias_candidates` | `alias_version`、`kind`、`alias`、`exposure_key`；只用于 `ambiguous`，列出所有候选家族 |

`resolveQuestion(session)` 返回 `{ result: "matched", exposureKey } | { result: "not_in_catalog" } | { result: "ambiguous", candidates } | { result: "unmatched" }`。不做近似匹配（RFC §7）。

- `matched` 与 `not_in_catalog` 都算“已解析”，不产生曝光不确定。`ambiguous` 与 `unmatched` 都算未解析，按 RFC §7 处理。
- `not_in_catalog` 必须经人工确认目录中没有同一题目家族；不能为了凑齐命中而修改冻结目录。

**首版别名（负责人 2026-11-01 确认）**：已知旧题共 7 道：`lib/pipeline/initial.ts:3-6` 的 3 个内置 ID，以及 `components/shell/new-essay.tsx:13-18` 的 4 道固定题（这 4 道只提交文字，按文字别名处理）。

| 旧题 | 结论 |
|---|---|
| `technology`（远程办公利弊）；固定题“工作与社会”（远程办公利弊） | `matched` → `qb_mock_work_002` 的家族 |
| `education`（大学是否免费）；`society`（年轻人迁往大城市）；固定题“科技与生活”“教育与成长”“环境与城市” | `not_in_catalog` |

用户自己粘贴的题目只做精确文字匹配，匹配不到就是 `unmatched`。

### 2.4 导入边界（负责人 2026-11-01 定，WP1 验收）

- `bank_version` 记录该题目版本首次收录的目录版本；后续目录重用同一题目版本时不改写，也不算内容冲突。
- 本次导入未包含的已有 ID 保持原状（不下架）；下架需另立契约。
- 重放旧目录不会降低当前版本：当前版本始终是已导入的最高版本。
- 同一会话的旧 ID 别名与精确文字证据指向不同结论时，返回 `ambiguous`（列出已知候选），由调用方按 RFC §7 处理；不按候选数量推断已解析。

## 3. 表结构（RFC §3 的落地）

全部新表只写进 `lib/db/schema.ts`，再用 `npm run db:generate` 生成**追加迁移**；`lib/db/initialize.ts` 保持为第一版基线，不再加新表（README “修改结构时”一节）。测试要覆盖空库全量迁移与已有数据库升级两种情况。只外键到 `users` 并级联删除的表，表示“删除一次练习后仍保留的无正文记录”（RFC §3）；外键到 `writing_sessions` 的表随练习一起删除。

| 表 | 主要列 | 删除练习时 |
|---|---|---|
| `attempt_markers` | `user_id`、`attempt_id`（PK 两列）、`activity`、`mode`、`question_id`、`question_version`、`exposure_key`、`primary_topic`、`question_type`、`created_at`、`deleted_at` | 保留，写 `deleted_at` |
| `completion_events` | PK `(user_id, attempt_id)`；`activity`、`exposure_key`、`question_id`、`primary_topic`、`question_type`、`completed_at`（可空，只限旧记录）、`original_submitted_at`、`freshness`（`fresh` / `repeat` / `unknown`）、`relation`（`none` / `continuation` / `rewrite`）、`legacy`、`evidence_deleted` | 保留，`evidence_deleted = 1` |
| `familiarity` | PK `(user_id, exposure_key)`；`first_attempt_id`、`first_attempt_at`、`deep_original_submitted`（`none` / `known` / `unknown_time`，`unknown_time` 表示旧记录提交过但时间不明）、`first_deep_original_at`、`fresh_attempt_id`、`prior_feedback`（`none` / `known` / `unknown_time`）、`external_practice`（`no` / `yes` / `unsure` / 空） | 保留 |
| `legacy_scan` | PK `user_id`；`cutoff_bank_version`、`alias_version`、`unresolved_count`、`scanned_at` | 保留 |
| `checkpoints` | `id`、`user_id`、`attempt_id`、`question_id`、`exposure_key`、`started_at`、`deadline_at`、`declaration`、`qualification_json`、`status`（`in_progress` / `eligible` / `ineligible` / `abandoned`）、`original_submitted_at`、`completed_at`、`is_baseline`；每位用户最多一条 `in_progress`（部分唯一索引） | 保留（分数等正文在会话里，随会话删除） |
| `default_continuations` | PK `(user_id, quick_attempt_id)`；`deep_attempt_id`、`created_at` | 保留 |

会话 JSON（`writing_sessions.state_json`）新增字段见 90 第 4.1 节。`completedAt` 只是 `completion_events` 的投影，读的时候以事件表为准。

## 4. 完成事件写入点（RFC §5）

| 活动 | 写入位置 | 条件 |
|---|---|---|
| 精练 | `lib/pipeline/engine.ts` 原稿评估的**第一次模型调用**成功并通过校验之后（`engine.ts:51` 起）。这一次已经返回分数、问题、原因与提示，满足 RFC §5 的“分数与可操作的问题反馈” | 原稿；第一次；同一事务写会话（`evaluation`、`stage = feedback`）与 `completion_events` |
| 速刷 | 13 第 6 节检查结果提交事务 | 第一次通过当前版本 |

- **第二次调用（提纲回顾）是可选步骤**（RFC §5）：改为独立的 `reviewStatus`（`none` / `pending` / `ok` / `failed`）与单独的重试动作，失败只影响回顾区，不回退阶段、不重跑评分、不影响完成。这是编排与保存边界的调整，评分与诊断的输入不变（G-01）。
- **原稿接受时**（`engine.ts:46` 附近，`state.submitted.original` 写入时）在同一短事务里，按顺序：
  1. 读取该家族已有的 `familiarity`；
  2. 计算本次资格：关联重写，或已有提交（`deep_original_submitted` 为 `known` / `unknown_time`），或已有反馈（`prior_feedback` 为 `known` / `unknown_time`）→ `repeat`；否则若家族曝光未知（RFC §7）→ `unknown`；否则 → `fresh`；
  3. **无论结果如何**都写入本次不可变的 `originalSubmittedAt`，并把 `deep_original_submitted` 置为 `known`（已是 `unknown_time` 的保持不变）；`fresh` 时另写 `fresh_attempt_id`；
  4. 资格按练习保存在会话（`originalFreshness`）与之后的完成事件里；评分重试读取保存的值，不重新计算。
- 粘贴题目也先经 `resolveQuestion`；能解析到家族时按该家族判定，避免绕过重复判定。
- 旧记录（RFC §5 末段）：`stage = finished` 的旧会话在迁移扫描时补一条 `legacy = 1, completed_at = null` 的事件；**不从 `createdAt`、`updatedAt` 推算时间**。有原稿提交或评估的旧会话，把对应家族的 `deep_original_submitted`、`prior_feedback` 记为 `unknown_time`。**已有完成事件**的旧会话被重评时，只写 `feedbackUpdatedAt`，不新建事件、不填日期。**没有完成事件**的旧会话（例如原稿提交过、评分一直失败），迁移后第一次满足反馈合同时，照常原子写入一条当前 `completed_at` 的完成事件；未知的历史提交时间保持为空（RFC §5 末段）。

## 5. 推荐（RFC §6）

### 5.1 函数

纯函数，放在 `lib/rules/recommend.ts`；输入一次性组装好，不读数据库、不读当前时间。

```ts
type RecommendInput = {
  topic: string;
  questions: QuestionRow[];          // 当前版本、is_current
  attempts: AttemptView[];           // 该用户全部未删除会话的摘要（activity、questionId、exposureKey、lifecycle、lastStudentActionAt、createdAt、card 状态、是否有进行中的改写）
  completions: CompletionEvent[];    // 含 evidence_deleted
  familiarity: FamiliarityRow[];
  continuations: DefaultContinuation[];
  quickEnabled: boolean;             // 有效开关：QUESTION_BANK_ENABLED 且 QUICK_ENABLED
  focusEnabled: boolean;
  focusEvidence: FocusEvidence | null; // 见 5.3；focusEnabled=false 时为 null
  excludedCodes: string[];           // 由 profile.excludedMemoryIds 中 "issue:XXX" 去掉前缀得到
};

type Recommendation =
  | { kind: "resume"; attemptId: string }
  | { kind: "new"; questionId: string; activity: "quick" | "deep"; continueFromQuickId: string | null; needsExplicitNew: boolean; focus: FocusChoice | null; reason: ReasonParts }
  | { kind: "rewrite"; questionId: string; rewriteOfDeepId: string; sourceDeleted: boolean; reason: ReasonParts }
  | { kind: "empty"; reason: "no_practice_questions" | "only_saved_or_unavailable_work" };
```

分支顺序、阻挡条件、打平规则、活动选择全部照 RFC §6 实现，代码注释写明对应 RFC 的哪一条。`resume` 只导航到已有练习，不调用创建接口。

**分阶段上线时**（RFC §1 允许分阶段，但必须写明关闭的功能）：`quickEnabled = false` 时，RFC 规定推荐速刷的情形一律改为推荐精练，`continueFromQuickId` 为空；只读的速刷练习不进入 `resume` 分支，也不算阻挡（它们无法被继续），只在练习历史中显示。

### 5.2 理由文字

`ReasonParts` 是结构化的（分支、题型是否练得最少、写作重点的两篇证据及日期），由前端 `components/topics/reason.tsx` 拼成中文。日期一律来自证据；不出现“最近”“经常”。

### 5.3 写作重点

- 本版本**默认关闭**：环境变量 `FOCUS_ENABLED`，默认 `false`。关闭时 `focus` 恒为 `null`（RFC §1、§6）。
- 打开前提（单独工作包，不在本次 N0～N3 内）：诊断输入带版本化分类表、输出按分类表校验；然后再按 RFC §6 选两篇新原稿。
- `FocusChoice = { code; taxonomyVersion; evidence: [{attemptId, submittedAt}, {attemptId, submittedAt}] }`。写入会话时转换为现有 `Focus`（`{code, name, instruction, reason}`，`lib/prototype/types.ts:24`），`name`、`instruction` 取自 `lib/taxonomy.ts`，`reason` 由 5.2 生成。

## 6. 检查点（RFC §7）

- 默认关闭：环境变量 `CHECKPOINTS_ENABLED`，默认 `false`；第 9 节检查点用例全部通过后才打开（RFC §1）。
- 所有创建练习的入口（主题推荐、自由选择、粘贴题目、写成作文）都先检查同一家族是否有进行中的检查点，有则拒绝（RFC §7）。
- 外部练习自报为 `yes` / `unsure` 时，即使这次没有开始检查点，也把自报写入 `familiarity.external_practice`。关闭或删除进行中的检查点时释放占位。
- 纯函数 `lib/rules/checkpoint.ts`：`checkpointState(input, now) → { state: "not_due" | "available" | "deferred" | "in_progress" | "unavailable"; candidateQuestionId?: string }`。
- 跳过：`profile.checkpointDeferredUntil = now + 7 天`。
- 开始：`POST /api/checkpoints/start { questionId, declaration: "no" | "yes" | "unsure", idempotencyKey }`。在一个事务里：重算资格（不先写本次曝光）、插入 `checkpoints(in_progress)`（部分唯一索引保证每人一条）、创建 `activity=deep, mode=mock` 会话、写 `attempt_markers` 与 `familiarity`。不合格返回 `409 checkpoint_ineligible` 并附原因。
- 计时：`deadline_at = started_at + 40 分钟`，服务端时间。原稿提交时比较服务端接收时间与 `deadline_at`；超时仍可评分，但 `status = ineligible`。客户端的 `elapsed` 只用于显示。
- 完成：原稿完成事件写入的同一事务里复核资格，写 `status`、`completed_at`；用户第一条 `eligible` 记录 `is_baseline = 1`，之后不改。
- 进展页（`app/(main)/progress/page.tsx`）：基线与趋势只用 `eligible`；其他模考单独列出并说明原因。

## 7. 迁移与扫描（RFC §9）

- `scripts/migrate-0.4.ts`（启动时也会对未扫描的用户执行一次）：对每位用户读出全部会话，经 `readSession` 适配；用别名表解析旧题目；写 `attempt_markers`、`familiarity`、旧完成事件；无法解析的旧练习计入 `legacy_scan.unresolved_count`。**不改写任何会话 JSON**。
- `unresolved_count > 0` 时，扫描时题库里所有 `exposure_key` 对该用户都算“曝光未知”（RFC §7）。之后新增的家族不受影响。
- 新注册用户直接写一条 `unresolved_count = 0` 的 `legacy_scan`。

## 8. 接口

| 方法与路径 | 说明 |
|---|---|
| `GET /api/topics` | 主题列表：已完成的不同题数、只开始过的题数、通过卡片数、草稿与未复查卡片数、最近一次练习日期或“还没练过” |
| `GET /api/topics/{topic}` | 该主题的普通题与保留题（保留题带标记）、每题的标记与尝试列表、`Recommendation` |
| `POST /api/sessions` | `{ questionId, activity, mode, idempotencyKey, rewriteOfDeepId? }`；`activity=quick` 时 `mode` 必须是 `practice`；`mode=mock` 只能经检查点接口或标为“重复模考”；按 `idempotencyKey` 去重 |
| `POST /api/sessions/{id}/lifecycle` | `{ action: "setAside" | "resume" | "close" }` |
| `POST /api/checkpoints/start`、`POST /api/checkpoints/skip` | 第 6 节 |
| `GET /api/sessions` | 不变 |

所有写接口：`assertSameOrigin`、从 Cookie 取用户、Zod 校验、他人资源返回 404。粘贴题目入口保留，但这类练习没有 `questionId`，不进入主题统计与推荐。

## 9. 测试对应

RFC §10 验收表的每一行都要有自动测试，测试名里写出该行的“情境”文字。规则部分在 `tests/recommend.test.ts`、`tests/checkpoint.test.ts`、`tests/practice-facts.test.ts`；涉及事务与删除的在 `scripts/test-db.ts`。另外补充：

| # | 情境 | 期望 |
|---|---|---|
| 1 | 原稿评估第一次调用成功，提纲回顾调用失败 | 已有一条完成事件；回顾区显示失败与重试；重试成功不新增事件 |
| 1b | 原稿评估第一次调用失败 | 没有完成事件；`originalSubmittedAt` 与新原稿资格已保存，重试不改变它们 |
| 1c | 旧会话原稿已提交、评分一直失败；迁移后重试成功 | 写一条当前日期的完成事件；`original_submitted_at` 为空 |
| 1d | 家族曝光未知时提交原稿，之后历史解析为已知 | 本次仍是 `unknown`；该家族已记为提交过，之后的提交是 `repeat` |
| 1e | 家族已有反馈记录（`prior_feedback = known`）但没有提交记录 | `repeat` |
| 2 | 两个标签页同时以自由选择开始同一家族的精练并提交 | 只有一篇是 `fresh` |
| 3 | 主题内所有普通题只有已复查通过、之后又被编辑的卡片 | 推荐 `resume` 其中一张（按 RFC 排序），不是空结果 |
| 4 | 两张草稿卡片在同一道题上 | `resume` 返回最近被学生编辑的那一次的 `attemptId` |
| 5 | 旧的已完成会话被重评 | 没有新完成事件；本周计数不变 |
| 6 | 导入两次题库 | 结果相同 |
| 7 | `FOCUS_ENABLED=false` | 所有推荐的 `focus` 为 `null` |
| 8 | 题库打开、速刷关闭，主题从没练过 | 推荐精练；已有的只读速刷不出现在继续入口 |
| 9 | 题库与速刷都打开，同一主题 | 照 RFC 推荐速刷 |
